# SkillYard 1.0 产品契约

> 本文件是 SkillYard 1.0 当前最高层产品边界，定义产品向用户承诺什么。详细执行规则见 [1.0 接管与管理权设计](1.0-management-authority.md)，文档层级见 [文档索引](README.md)。

## 产品定义

SkillYard 1.0 是面向 Apple Silicon（`arm64`）Mac 的本地桌面应用，目标系统为 macOS 14 Sonoma 及以上：发现本机 AI Agent Skills，让用户把希望统一维护的 Skill 安全接管到一个本地管理体系中，并完整负责本地主副本、挂载、更新和 Bundle 删除。Intel（`x86_64`）、Universal 2 构建和 macOS 13 及更早系统不属于 1.0 支持范围。

它不是只读清单，也不是只提示更新的来源收藏夹。安装与完整生命周期管理是 1.0 的核心产品能力。

SkillYard 1.0 使用 Tauri 2 构建。TypeScript Web UI 作为展示与交互层，静态资源打包在应用内并由 macOS 系统 WKWebView 加载；生产应用不启动 localhost Server，也不捆绑 Chromium、Python runtime 或 Python sidecar。

所有持久化状态和高风险本机操作都由小而封闭的 Rust Lifecycle Core 负责，包括 SQLite、Source 获取、本地扫描、候选内容验证、Bundle 事务、软链接、Filesystem Transaction Journal 和中断恢复。TypeScript UI 只能调用类型明确的业务命令并展示返回状态，不能直接获得通用文件系统、SQL 或 shell 能力，也不能绕过 Plan、确认和事务边界。1.0 不使用 Tauri localhost plugin，不向前端暴露通用 `fs`、`sql` 或 `shell` plugin。

`SkillYard.app` 是 1.0 唯一的用户入口。1.0 不提供 `skillyard` CLI、headless 模式、独立 daemon、localhost API、公开 Rust API 或单独安装的恢复工具；扫描、安装、接管、Mount 管理、更新、删除和中断恢复都必须在 App 内完成。Lifecycle Core 只是 `.app` 内部实现边界，测试可以直接验证其模块，但这不会形成面向用户或第三方的稳定命令与 API 契约。

SkillYard 1.0 的官方公开发布物是 GitHub Releases 中面向 Apple Silicon 的 ZIP。发布流程在内部使用 SHA-256 校验同一份候选 ZIP，但不把校验文件作为公开下载资产。发布构建使用 ad-hoc signing，不加入 Apple Developer Program，也不承诺 Developer ID、Hardened Runtime、Apple notarization、stapling 或无警告的 Gatekeeper 安装体验；首次打开时可能需要用户按 macOS 的正常 Gatekeeper 流程确认。

发布构建和验收测试只产生并验证 `arm64` 应用，最低系统版本固定为 macOS 14。不能在不受支持的 Intel 或旧系统上依赖 Rosetta、运行时警告或“可能可用”来代替明确拒绝运行。未来扩展架构或降低最低系统版本需要新的支持决策，不能被视为 1.0 的补漏。

1.0 不进入 Mac App Store，也不启用 App Sandbox。首次扫描、接管和 Mount 管理需要持续访问 `~/.codex/skills`、`~/.claude/skills`、`~/.copilot/skills`、已登记 Project 和固定 Central Store。所有操作仍受当前 macOS 用户权限、TCC、POSIX ACL 和 System Integrity Protection 约束；无法访问时必须在首次变更前失败，不能提权或绕过系统保护。

SkillYard 1.0 不提供 Application Update、应用内更新源或下载安装器。用户需要更新应用本体时，从 GitHub Releases 下载新的官方 ZIP 并手动替换 `SkillYard.app`。手动替换不能修改 Central Store、SQLite、Current Content、Filesystem Transaction Journal 或 Mount；新应用启动后仍先执行普通事务恢复。

因此，1.0 界面中的“检查更新”和 Bundle Update 只指 Skill Source 内容，不能被解释为检查或替换 `SkillYard.app`。GitHub Releases 是唯一官方下载渠道，不代表应用具备自动更新能力。

“1.0 尽量简洁”不是把产品缩成演示版，而是只保留让核心生命周期完整、可靠且日常可用的能力。首次扫描与 Inventory、直接安装或接管、按 Bundle 查看 Skill、Mount 管理、Source 关联与检查、完整 Bundle 更新、删除 Source、删除 Bundle、中断恢复属于主流程；只有直接保证这些流程可用、状态正确或用户内容安全的界面和数据才进入 1.0。便利性增强和外围能力后置，但不能以简化为理由删除确认、验证、事务恢复或管理权边界。

## 1.0 对用户的承诺

### 首次使用由用户开始扫描

SQLite 中没有首次扫描完成记录时，SkillYard 先显示简短的首次使用介绍页，说明扫描范围、只读性质和不会自动接管，并提供一个“开始扫描”按钮。用户点击前，应用不扫描本机 Skill 目录。

用户点击后，SkillYard 执行首次本地只读盘点，保存扫描完成状态和发现结果，然后进入 Skill 列表。即使没有发现 Skill，也要记录首次扫描已经完成，避免下次启动重新进入介绍页。首次扫描不访问 GitHub、`skills.sh` 或其他上游服务。

某个扫描根或其中单个 Skill 暂时无法读取时，SkillYard 继续扫描其他根和同根中的其他 Skill，并把可用清单与按路径区分的扫描告警一并保存；首次扫描仍然完成并进入清单。条目级问题只保留该 Skill 的上次观察并标记为 stale，扫描根级问题才保留该根的全部上次观察。扫描不会自动修复、删除或跟随损坏链接；用户修复路径并主动刷新后，对应告警应独立消失。

SQLite 中已经存在首次扫描完成状态时，后续启动不再显示介绍页。应用先恢复任何未完成的生命周期事务，再执行已有 Mount 的启动健康检查，随后展示之前扫描、配置或选择的 Skill；启动不会查询上游更新。

### “刷新本机”与“检查更新”是两个动作

用户点击“刷新本机”时，SkillYard 只重新扫描 Codex、Claude Code、GitHub Copilot 的已配置 global、project 和只读证据目录、Codex 官方插件缓存，以及已登记 Project 中的对应 Skill 目录。它重新读取本地 Management Evidence、更新 Inventory，并检查已有 Mount 的健康状态，从而发现用户在应用外通过 `npx skills`、`gh skill`、Lark CLI 或其他方式新增、移除或改变的本地 Skill。

“刷新本机”不访问 GitHub、`skills.sh` 或其他上游，不自动接管、搬迁、安装、删除受管内容或修复任何 Skill。新发现的内容只按证据显示为待接管、Agent 应用管理或项目仓库管理，后续操作仍需用户单独发起。

“检查更新”只查询已经登记并关联本地 Bundle 的上游 Source，判断上游是否发生变化；它不重新扫描本地安装目录。应用启动先恢复未完成事务，再执行已登记 Mount 的轻量健康检查；两者都不等同于一次完整的“刷新本机”，也不执行“检查更新”。

### 主界面以 Bundle 为列表，进入后管理 Skill

扫描完成后的主界面第一层只展示 Bundle 或只读管理分组，不平铺其中全部 Skill。由 SkillYard 管理的本地安装以 Bundle 卡片出现，每张卡使用 Bundle Display Name，展示成员数量、更新状态和 Bundle 级操作；用户进入 Bundle 后才看到 Skill 成员列表，再进入单个 Skill 查看来源、路径、Metadata、安装收据和 Mount。每个 Skill Identity 只在所属 Bundle 详情中出现一次。

待接管条目存在确定性 Installation Chain 时按来源显示为一个待接管 Bundle；没有分组证据时，每个候选保持为独立的一成员待接管 Bundle，不能按同名自动合并。Codex 官方插件中的 Skill 以插件名组成只读 Bundle 分组；其他 Agent 应用管理和项目仓库管理的内容仍按管理方或项目形成只读分组。只读分组不创建 SkillYard 本地 Bundle，也不获得安装、更新、挂载或删除入口。

Bundle 标题代表一个本地已安装组。通过 `.agents/.skill-lock.json` 接管时，规范化 `sourceUrl` 用于确定同一来源身份，lock 中的 `source` 直接作为 Bundle Display Name；可选 `pluginName` 不拆分 Bundle，也不改变 1.0 的名称。用户确认接管后，已核验的 GitHub lock 来源必须在同一 SQLite 提交中创建或复用 Source、关联本地 Bundle，并保存能够确认的成员路径；不能只把来源留作界面文案或安装履历。lock 没有 ref 时以 `HEAD` 作为首次可检查的跟踪入口，首次完整更新再建立已采用的上游基线。若 Bundle 仍关联 Source，详情页可以另外展示该 Source 中尚未安装的可用 Skill；这些远端成员在安装前不属于本地 Bundle。直接安装时默认选择 Source 中的全部 Skill；接管已有安装时只保留本机已经安装的成员。用户主动更新 Bundle 后，关联 Source 中全部通过验证的当前 Skill 都会被安装，不提供成员排除。SkillYard 1.0 不提供本地版本历史或回滚。

主界面默认覆盖本机已有或已经安装的全部 Skill，但只通过上述 Bundle／管理分组进入。来源中仅为可用、尚未安装的成员不进入主列表。用户可以按管理状态筛选并按 Bundle 或成员关键词搜索；命中成员时只显示其所属分组，不把 Skill 重新平铺到第一层。筛选和搜索不能改变 Skill 的管理方、安装状态或使用关系。“重置应用”和“打开 Central Store”只出现在设置页，不作为主界面的常驻操作。一次更新准备或检查失败后的内联提示可以由用户关闭；它不能在操作已经结束后持续阻挡浏览或后续操作。

生命周期事务运行期间，主界面和详情页仍可浏览、搜索、筛选和切换 Bundle／Skill。界面顶部持续显示当前操作，并提供返回该操作进度页的入口；受影响条目显示“处理中”，不能提前显示最终结果。所有会写入 SQLite、Central Store、Source 状态、Inventory 或 Mount 的入口暂时不可执行，包括“刷新本机”“检查更新”、在线来源重新加载和其他生命周期操作。事务结束后，界面再读取最终状态并恢复这些入口。

### 看清本机有什么

SkillYard 扫描内建 Supported App 表中的 Agent 应用、全局目录、项目目录和常见安装工具留下的证据，展示 Skill、Source、Bundle、所在位置、项目使用关系与当前管理方。

SkillYard 1.0 的 Supported App 表固定包含 Codex、Claude Code 和 GitHub Copilot。每个应用配置记录显示名称、固定的应用专属 global Mount 根目录、固定的应用专属 project Mount 根目录、只读兼容目录、已知路径重叠关系，以及可选的安装检测方式。1.0 的写入路径固定如下：

| Supported App | global Mount 根目录 | project Mount 根目录 |
| --- | --- | --- |
| Codex | `~/.codex/skills` | `<project>/.codex/skills` |
| Claude Code | `~/.claude/skills` | `<project>/.claude/skills` |
| GitHub Copilot | `~/.copilot/skills` | `<project>/.github/skills` |

大多数应用只是路径配置；只有路径或识别规则确实特殊时才增加专门逻辑。

安装检测只显示应用“已检测到”或“未检测到”，不能自动创建新的 Supported App。一个应用存在多个有效目录时，由同一份应用配置在内部处理，用户仍然只看到一个可勾选的应用。只有用户确实需要分别选择两个挂载目标时，SkillYard 才把它们定义为两个应用；1.0 不建立 Host Family、Runtime Surface 或品牌层级。

“支持某应用”只承诺 SkillYard 能正确管理该应用的本地 Skill 目录，不代表支持该品牌的全部云端、IDE、插件或其他能力。用户勾选一个 Supported App，表示允许 SkillYard 向上表中该应用的固定路径写入 Mount；这不是“只有这个应用可见”的保证。如果其他 Supported App 也会兼容扫描该路径，界面必须在确认前提示还可能被哪些应用发现。1.0 不修改其他 Agent 的启用／停用设置来强制独占可见。Codex 官方插件缓存是单独的只读展示面，不扩大 Supported App 的写入承诺。

SkillYard 必须区分 Skill 自己声明的 Skill Name 与 Agent 应用生成的 Host Presentation Label。例如本地 Skill 声明的是 `name: qa`，截图中的 `Mattpocock Skills: Qa` 则是 Codex 为插件、目录或分组上下文生成并格式化的 UI 标签；这个标签不构成重命名，也不能改变 Skill Identity。

SkillYard 的列表和搜索结果不直接复用任一 Host 的标签，而是统一生成 `Bundle Display Name: Skill Name` 形式的 SkillYard Presentation Label。详情页分别展示原始 Skill Name、所属 Bundle，以及 Codex、Claude Code 等各 Host 实际使用的 Host Presentation Label。

1.0 的 Bundle Display Name 在 Bundle 创建时取来源输入中最直接的稳定名称：GitHub 仓库使用 canonical `owner/repository`，package 使用 package name，ZIP 和本地目录使用去掉扩展名的 basename。Source 后续被删除时该名称继续保留。它不使用 AI 推断、名称优先级或用户自定义。

SkillYard 创建 Mount 时，Host 目录中的软链接叶子目录名直接使用 Skill Name。Bundle Display Name、SkillYard Presentation Label 和 Host Presentation Label 都只用于界面展示，不会被写入 Mount 目录名。1.0 不添加 Bundle 前缀、自动后缀或别名；同名路径已被占用时进入 Mount Conflict。

### 一律接管、按需搬迁

用户提供的整个仓库或完整上游登记为一个 Source。用户确认安装或接管已有内容时，SkillYard 才创建对应的本地 Bundle，并统一控制其中已安装 Skill 的当前主副本、挂载和本地生命周期。

- 已经位于合适 Central Store 的内容不做无意义搬运，只完成登记并校正链接。
- 散落的内容只有在用户确认接管计划后，才通过可恢复事务搬迁，并把原有 Host 使用位置替换为软链接 Mount。
- 扫描永远不能静默移动、覆盖或删除用户文件。

接管已有安装时，Skill 已经出现在至少一个 Host 路径中。SkillYard 必须识别并保留这些现有使用关系：完成主副本接管后，在原 Host 位置重建指向 SkillYard-managed content 的软链接，而不是让用户重新选择一次已有 Host。

如果扫描发现同一个 Skill 有多个本地副本，SkillYard 最终只接管一个主副本。内容相同时可以直接合并使用关系；内容不同时，必须由用户选择其中一份内容。选定后，只有该内容作为这个成员进入完整候选 Bundle；Bundle `current` 生效后，所有现有使用位置统一改为指向该成员稳定受管路径的 Mount，不能让某个位置继续保留未选中的副本。未选中的内容只在接管事务验证完成前作为临时恢复副本存在，成功后清理，不形成可选旧版。用户不接受统一或没有完成选择时，不执行接管，也不修改任何副本。

如果几个来源未知的本地副本名称相同，但 SkillYard 没有确定性证据证明它们属于同一个 Skill，不能自动合并。界面允许用户手动确认“它们是同一个 Skill”；确认后建立一个本地 Skill Identity，并进入上述选择唯一主副本、统一全部位置的流程。用户不确认时，各副本继续作为不同 Skill 展示。这个确认不推断 Source、Bundle Member 或上游更新标识，来源状态仍为“来源未知”。

接管多个来源未知、且彼此是不同 Skill 的已有安装时，只有 receipt、lock、安装 manifest、经过核验的 Adapter 结果或其他确定性 Management Evidence 能证明它们来自同一安装组，SkillYard 才把它们放进同一个 Bundle。没有这类证据时，每个 Skill 分别创建一个 Bundle。它们碰巧位于同一个 Supported App Skill 根目录、共享父目录、名称相似或位置相邻，都不能作为自动归组依据。接管计划必须在用户确认前展示最终 Bundle 边界，因为该边界同时决定后续的原子更新和级联删除范围。

如果已有安装位于 `~/.agents/skills` 或项目 `.agents/skills` 等多应用共享扫描目录，接管计划必须让用户选择希望由 SkillYard 维护 Mount 关系的 Supported App，并展示每个选择对应的固定应用专属目标路径。共享目录只用于扫描和接管，不能保留为接管后的 Mount，也不能接收新的 Mount。影响预览仍须提示应用专属目标可能存在的交叉可见性。事务备份原共享入口，把内容登记或迁入 Central Store，再在所选应用的固定路径创建并验证 Mount；只有全部验证成功后才能移除原共享入口。任一步失败都恢复共享入口，并撤销本次新增 Mount。

完整接管流程定义在 [接管与管理权设计](1.0-management-authority.md)。

### 提供真正的安装

“安装 Skill”进入一个参考 cc-switch 的“发现 Skill”页面，而不是只有一个任意来源输入框。页面提供：

- “仓库”视图：浏览已经添加的 GitHub 来源，并通过来源管理添加 `owner/repo`、GitHub URL 和可选 branch；
- `skills.sh` 视图：搜索外部发现服务，并把结果解析为可登记的 Source；
- 本地与其他来源入口：ZIP、本地目录、URL，以及接管已有安装。

用户可以粘贴 GitHub 仓库根 URL，也可以粘贴包含 branch 和子目录的 Skill URL。SkillYard 从中解析仓库、ref 和路径，但始终把完整仓库登记为 Source；子目录只用于定位和高亮对应 Skill，不会形成独立 Source。只有用户确认安装后才创建本地 Bundle，直接安装仍默认选择 Source 中的全部成员。

首次登记 GitHub Source 时，URL 或用户输入中明确提供的 ref 优先，并且必须验证为可访问。没有提供 ref 时，GitHub Adapter 读取仓库当前的 default branch，并把解析出的实际 branch 名保存为 Tracked Ref；SkillYard 不猜测 `main` 或 `master`，也不保存会随仓库设置自动漂移的“default”占位值。无法解析有效 ref 时不能完成 Source 登记或安装。

Source 按 canonical upstream 唯一。推荐列表、`skills.sh` 结果、GitHub 仓库 URL、成员 URL、已有安装证据或其他入口只要解析到同一个上游，就必须复用同一个 Source；新的入口只补充发现证据、Installation Chain 和成员定位提示。一个 Source 在本机最多关联一个 Bundle。该 Source 已有关联 Bundle 时复用现有本地安装组；尚未安装或 Bundle 已被删除时，不预先创建 Bundle。对于 GitHub，同一仓库即使通过不同 URL、ref 或子目录到达，也仍是同一个 Source。

每个 GitHub Source 同时只保存一个 Tracked Ref。新入口包含不同 ref 时，SkillYard 显示当前 ref 与新 ref，但继续保留当前设置；只有用户明确确认“切换跟踪 ref”后才保存新值。新 ref 必须先被 GitHub Adapter 验证为可访问，否则不改变任何状态。确认切换只改变后续成员发现、检查更新和更新获取的目标，不替换当前受管内容，也不修改 Mount。

SkillYard 1.0 的 GitHub Source 只支持公开仓库。应用不提供 GitHub 登录，不读取或保存 access token，也不尝试访问私有仓库。用户已经在本机取得的私有内容仍可通过本地目录或 ZIP 作为 Source 导入。

1.0 的“URL”安装只接受能够由已支持 Adapter 确定解析的地址：公开 GitHub 仓库或成员路径、可直接下载的 ZIP 或 `.skill` 文件，以及已支持的官方 Skill index/manifest。普通网页、推特或论坛帖子不是安装源；SkillYard 不抓取页面并用 AI 猜测下载地址。

仓库和 `skills.sh` 的发现结果都按 Source 分组展示，而不是组成一张跨来源的扁平 Skill 卡片列表。安装页首次打开只展示每个 Source 的摘要和成员数量，成员列表默认折叠，用户点击对应 Source 的“查看 Skill”后才展开；`skills.sh` 命中先解析到对应 Source，同一 Source 的多个结果合并，并在组内高亮匹配的 Skill。进入安装确认时默认选择该 Source 的全部 Skill，用户仍可在确认前取消不需要的成员。

发现入口解析到一个已有 Source 时，SkillYard 复用该 Source。若它已经关联本地 Bundle，页面同时展示现有安装和挂载状态，已安装成员不能再次被选择安装；用户只能选择尚未安装的可用成员。若它没有 Bundle，用户确认安装后创建新的本地 Bundle。已有成员需要采用新内容时必须使用正式更新流程，安装不能覆盖其当前受管内容或 Mount。

SkillYard 1.0 直接采用 cc-switch `3.17.0` 当前内置的四个 GitHub Source，首次使用时作为已添加来源存在：

- `anthropics/skills`，branch `main`；
- `ComposioHQ/awesome-claude-skills`，branch `master`；
- `cexll/myclaude`，branch `master`；
- `JimLiu/baoyu-skills`，branch `main`。

它们作为“仓库”视图的初始内容。推荐列表只是本地配置，不托管 Skill、不依赖 SkillYard 远程服务，也不构成公共 registry。这些初始来源与用户后来添加的来源采用相同规则，可以维护或删除；1.0 不建立启用／停用状态。

SkillYard 不在应用启动、首次扫描或打开“安装／发现 Skill”页面时访问这些初始来源。安装页只从 SQLite 读取 Source 摘要、成员数量和上次成功保存的目录 metadata；只有用户点击某个 Source 的“重新加载来源”时才访问该上游。`skills.sh` 只在用户提交搜索时访问，不在后台预取或轮询。“重新加载来源”是发现页的局部动作，不是主界面的“刷新本机”。

网络 Source 的成员目录只在一次完整获取和验证成功后替换。重新加载失败时，SkillYard 保留上次成功目录及其获取时间，标记“刷新失败”，不能把错误、超时或空响应解释为成员已被删除。旧目录仍可浏览，但属于 Stale Source Catalog；在新的 Source 获取成功前，用户不能根据它安装新 Skill 或执行 Bundle Update。已安装 Bundle、Skill、Mount 和当前受管内容完全不变。这个目录只是保存在 SQLite 中的发现 metadata，不是 Skill 内容缓存或 SkillYard 托管的公共 registry；从未成功加载过的 Source 没有可展示的旧目录，只显示本次错误。

用户可以从 GitHub、`skills.sh`、URL、ZIP 或本地目录发起安装。SkillYard 通过 Adapter 获取内容，在临时区验证后保存为当前受管内容，再供 Host 或项目挂载使用。

从 SkillYard 直接安装时，最终选择的全部 Skill 先共同组成一个完整的候选 Bundle，写入 Central Store 中的 Managed Bundle Directory，并在验证成功后通过该 Bundle 唯一的 `current` 软链接一次生效。用户随后可以为每个 Skill 勾选零个或多个需要维护 Mount 的 Supported App，以及对应的全局或项目范围。SkillYard 只在所选应用路径创建指向 `current` 下稳定成员路径的软链接 Mount，不会把实体主副本直接安装到应用目录。

这里复用的是 cc-switch 的发现与来源管理体验，不是它的本地生命周期行为。SkillYard 不会在安装完成后立即挂载到某个当前 Agent，不会把 Bundle 扁平化成无关联的 Skill，不会让 ZIP 绕过成员选择，也不会在软链接失败时退化为 copy。完整对照见 [cc-switch 3.17.0 Skill 管理机制核验](research/cc-switch-skill-management.md#1-安装与发现入口)。

SkillYard 不在扫描、接管、安装、验证或更新过程中执行 Skill 携带的 shell、Python、Node 脚本、二进制文件或 lifecycle hook。它只读取并保存这些文件。影响预览必须提示本次内容中检测到的脚本或可执行文件；该提示只说明内容构成，不是恶意代码扫描或安全保证。Skill 被挂载后，Agent 应用是否按 Skill 指令执行其中代码，仍由对应 Agent 和用户决定。

Skill Member 目录只允许包含普通目录和普通文件。任何软链接、硬链接、FIFO、socket、设备文件或其他特殊文件系统条目都会使该 Skill 验证失败，即使链接目标仍在目录内部也不例外。SkillYard 以不跟随链接的方式检查内容，不自动展开、复制、转换或修复这些条目，也不提供忽略错误继续安装的选项。直接安装或接管时，失败成员不能进入最终确认计划，原目录不被修改；更新或手动替换时，任一候选成员失败都会在切换 `current` 前终止整个 Bundle 操作，现有受管内容和 Mount 保持不变。SkillYard 自己创建的 Bundle `current` 和 Host Mount 不属于 Skill 内容，不受这条限制。

ZIP 或其他归档中的每个条目必须使用规范化后仍位于本次临时区内部的相对路径。绝对路径、规范化后逃出临时区的路径，或者声明为链接及其他特殊文件类型的归档条目，会使整个输入在解压和成员发现前失败；SkillYard 不向临时区之外写入任何内容，也不提供强制继续入口。

SkillYard 对网络获取和归档展开执行四个固定的 Source Resource Limit：累计接收最多 100 MiB、归档最多 20,000 个条目、展开后的普通文件总量最多 512 MiB、单个普通文件最多 100 MiB；`1 MiB = 1,048,576 bytes`。这些值内置于 1.0 本地构建并保持为产品常量，用户不能修改，也不能在超限后选择强制继续。验证必须在流式接收或写出每个条目时累计，不能先完整占用磁盘再检查。任一限制被触发时，本次 Source 获取、安装或更新在写入 Current Content 前失败，清理临时内容；已有 Bundle、Member Selection 和 Mount 保持不变。界面只需指出触发的限制和实际已检测值，不提供容量配置页面。

macOS 1.0 的 Central Store 根目录固定为 `~/Library/Application Support/SkillYard/`。其中每个 Bundle 的 Managed Bundle Directory、完整当前受管内容和唯一 `current` 是用户已接管 Skill 的实际主副本，不是缓存或可随应用清理的普通数据。SQLite、临时区、事务恢复临时内容和 Filesystem Transaction Journal 也使用 SkillYard 控制的独立子路径，默认位于同一本地文件系统。界面提供“在 Finder 中打开”，但 1.0 不允许修改位置、迁移到其他目录或使用外置磁盘作为 Central Store。

Central Store 根目录持续保存由 SkillYard 生成的 `SKILLYARD-INFO.md`。文件必须明确说明这里保存的是用户 Skill 的实际主副本、不能按缓存删除，并列出已知 Source 和 Host／project Mount 位置；相关管理关系成功变更后同步更新。它用于帮助用户和其他工具理解目录性质，不能替代 SQLite 或 Filesystem Transaction Journal。

Central Store 不能被 Agent 应用直接扫描。`~/.agents/skills` 和项目 `.agents/skills` 等会被多个 Agent 应用共同扫描的目录既不能作为主副本目录，也不能作为 SkillYard 新建 Mount 的目标；它们仅用于只读 Inventory、Management Evidence 和已有安装 Takeover。所有新 Mount 都写入上表中的应用专属路径。

接管和挂载只处理用户明确选择的单个 Skill 根目录。SkillYard 可以把 `~/.codex/skills/example-skill` 这样的成员目录替换为 Mount，但绝不能把 Codex、Claude Code 或 GitHub Copilot 的整个 Skill 根目录替换成软链接。Host 内置、插件管理、项目仓库维护以及其他未被用户选择的内容必须原样保留。

同一个 Skill 在同一个 Supported App 中只能采用一种 Mount Scope：一个 global Mount，或者位于一个或多个不同项目中的 project Mount。global Mount 与 project Mount 不能同时存在；不同项目的 project Mount 可以并存，不同应用的 Mount 关系分别记录。实际目标路径可能被多个应用共同扫描，因此“分别记录”不等于“彼此不可见”。普通挂载操作出现 Scope Conflict 时，用户需要先单独移除已有 Mount，再创建另一种 scope 的 Mount。

接管已有安装是唯一例外。如果扫描发现同一个 Skill 在同一个 Supported App 中同时存在 global 和 project 安装，接管计划必须让用户选择一种 scope。选择 global 时，事务保留或创建 global Mount，并移除原有 project 副本，相关项目统一通过 global Mount 使用该 Skill；选择 project 时，事务移除原有 global 副本，并把扫描到的项目位置统一改为 project Mount。两种选择都使用同一份当前受管内容。用户未选择时，不执行接管。

SkillYard 维护一份本地 Project 列表。项目只有在用户主动选择其根目录，并在应用弹窗中再次确认，或接管已有 project Skill 时识别到该项目并经用户确认后，才会加入列表；原生目录选择器返回路径时不能立即写入 Project 记录。SkillYard 1.0 不扫描整块磁盘来寻找项目。只有 Project 列表中的项目可以成为 project Mount 目标，SQLite 只需保存项目根目录。1.0 假设这些项目都位于本地、持续可访问的目录中，不建立 Project 不可用或 Mount 无法检查等额外状态。

项目加入列表后，SkillYard 立即只读扫描 Codex、Claude Code 和 GitHub Copilot 在该项目中的已知 project Skill 目录，展示已有 Skill、位置和当前管理方。此次扫描不能自动接管、搬迁、挂载或修改任何内容；用户希望管理其中某个 Skill 时，仍须单独发起并确认接管事务。

用户从 Project 列表移除一个仍有 SkillYard-managed project Mount 的项目时，SkillYard 必须先展示受影响的全部 Skill 和 Supported App。用户确认后，SkillYard 在一个可恢复事务中移除该项目的全部 managed Mount，验证完成后才删除 Project 记录。这个操作不删除 Central Store 中的受管内容，也不影响其他项目或应用中的 Mount；项目仓库或 Agent 应用自己管理的内容保持不变。

用户可以暂时不选择任何 Supported App。此时 Skill 保持“已安装、未挂载”：它仍然由 SkillYard 管理，可以重新挂载；Bundle 有关联 Source 时仍可更新，没有 Source 时不能更新。由于 Central Store 不被 Agent 应用扫描，该 Skill 不会通过 SkillYard 出现在任何 Agent 应用中。用户之后可以再为它添加 Mount。“已安装、未挂载”是使用状态，不是新的管理权类别。

SkillYard 1.0 不提供单独卸载或删除一个 Skill Member 的入口。用户移除最后一个 Mount 时，只解除对应 Host 的使用关系，Skill 回到“已安装、未挂载”；Managed Bundle Directory、Member Selection 和当前受管内容继续保留。受管内容只会在用户明确删除整个 Bundle 时随级联删除一起移除。

创建 Mount 前，SkillYard 必须检查目标 Host 路径。路径已经是该 Skill 的正确软链接时，只验证并校正记录；能够以稳定证据证明是同一 Skill、但尚未正确接管或链接时，转入需要用户确认的接管或链接校正计划。路径被其他内容占用或身份无法确认时，挂载必须停止，不自动覆盖，也不自动改名。即使占用路径的是另一个 SkillYard-managed Mount，1.0 也不提供“一键替换挂载”；用户需要先单独移除旧 Mount，再重新发起挂载，或取消本次操作。

Bundle 分组提供批量挂载入口，但 Bundle 本身不拥有一个统一 Mount。SkillYard 在确认前检查本次选中的全部 Skill 和目标路径；存在 Mount Conflict 的成员不能进入最终事务，用户可以把它从本次选择中排除，或者先处理占用路径后重新检查。最终确认的多个独立 Mount 作为一个可恢复事务执行。任一 Mount 在创建或验证阶段失败时，SkillYard 撤销本次已经创建的 Mount 并恢复事务开始前的记录，不能把部分成功显示为完成。

已经登记的 SkillYard-managed Mount 如果被外部删除、替换为普通目录，或不再指向该 Skill 在 Bundle `current` 下的稳定成员路径，SkillYard 保留 Mount 记录并标记 Mount Drift，不静默重建或覆盖。用户可以主动修复：目标路径为空时，确认预览后重建正确软链接；目标路径被占用时进入 Mount Conflict，必须先由用户处理占用内容。用户也可以正式移除这条 Mount 记录，而不影响 Managed Bundle Directory 和当前受管内容。

SkillYard 在应用启动时对全部已登记 Mount 执行一次本地只读健康检查，用户点击“刷新本机”时再次检查。1.0 不使用文件系统监听，也不在后台持续轮询 Mount；健康检查只更新检查结果，不能自动修复任何 Drift。这与上游更新检查相互独立，启动时仍然不会查询上游状态。

安装一个 Skill 不要求 SkillYard 先运营公共市场。1.0 可以使用用户提供的来源和现有发现服务，不自建公共 Skill registry。

从包含多个 Skill 的 Source 全新安装时，选择页默认勾选全部已发现成员，用户可以在确认前取消不需要的 Skill。接管已有安装时，只默认勾选本机原本已经安装的 Skill；Source 中其他成员保持可用但不被新增。只有用户确认后的结果才写入本地 Bundle 的 Member Selection。

如果用户确认的安装选择没有包含 Source 中全部已发现且有效的 Skill，SkillYard 必须在提交前提示：部分 Skill 可能依赖同一 Bundle 中未选择的其他 Skill，1.0 不检查这种依赖，继续后可能无法正常使用。用户仍可确认并继续，风险由用户承担。SkillYard 1.0 不解析 `SKILL.md` 链接、脚本、manifest 或其他内容来建立依赖图，不自动补选依赖，也不因部分安装而阻止事务。后续 Bundle Update 仍按既定规则安装 Source 的全部有效成员。

### 个人 Skill 在独立来源中编辑

用户可以把个人目录或自己维护的本地 Git clone 明确登记为 Editable Local Source。这个目录继续由用户编辑，SkillYard 不把它直接作为正在使用的主副本，也不让 Host Mount 指向它。

SkillYard 检测 Editable Local Source 与上次采用内容之间的变化，展示这次更新会安装的完整 Bundle；只有用户确认后，才准备包含全部当前成员和需要保留成员的完整候选 Bundle，并原子替换该 Bundle 唯一的 `current`。已有 Mount 自动跟随，新安装成员保持未挂载。Managed Bundle Directory 不是编辑工作区，直接修改其中内容不能作为一次有效更新。

明确由项目仓库维护的 Skill 仍属于 Project-managed Installation。只有用户明确把一个本地目录指定为个人可编辑来源时，才进入 Editable Local Source 工作流。

Editable Local Source 被移动、重命名或暂时无法访问时，SkillYard 将 Source 标记为“来源不可用”。该状态只暂停成员发现和本地修改捕获；现有受管内容与全部 Mount 继续工作，SkillYard 不自动解除挂载或删除受管内容。用户可以重新指定来源位置，但新路径必须先经过内容识别和确认，不能只因名称相同就静默关联。

### Source 是上游来源，Bundle 是本地已安装组

Source 保存完整仓库、ZIP、确定性 URL、Editable Local Source 或其他上游入口及其可用 Skill 目录。SkillYard 不根据 manifest、版本边界或 `SKILL.md` 数量把一个 Source 拆开。Source 可以在尚未安装任何 Skill 时独立存在。

Bundle 只在用户确认直接安装或接管已有安装后创建，保存 Central Store 中实际已经安装的 Skill。它是 SkillYard 的本地管理分组，不是远端目录的另一种名称。Bundle 可以在 Source 被删除后继续存在；此时所有 Skill、Mount 和当前受管内容保持不变，只是不能再从该 Source 检查或执行更新。

Source 与 Bundle 的关联是可选一对一：一个 Bundle 最多关联一个 Source，一个 Source 最多关联一个 Bundle。用户要把另一个没有 Source 的 Bundle 关联到已经绑定本地 Bundle 的 Source 时，SkillYard 不创建第二个 Source-backed Bundle，而是展示归并计划。计划列出两个 Bundle 的全部 Skill、Mount、重复身份、内容选择和路径冲突；未解决冲突或用户未确认时不修改任何内容。

归并事务把待归入 Bundle 的成员与 Mount 关系加入已有 Bundle，准备并验证已有 Bundle 的完整候选内容，再通过它唯一的 `current` 生效并校正 Mount。只有全部内容、Mount 和 SQLite 关系验证成功后，才删除已经为空的原 Managed Bundle Directory 和 Bundle 记录。这个清理不丢弃 Skill 内容，不属于 Cascading Delete，也不需要删除 Bundle 的两次危险确认；任一步失败或中断都按 Filesystem Transaction Journal 保留原状态或完成已经生效的归并。

Source 目录内每个文件名严格为 `SKILL.md` 的文件定义一个可安装 Skill，该文件的父目录就是 Skill 根目录。来源不需要额外提供 manifest；没有发现 `SKILL.md` 的 Source 没有可安装成员。Adapter 或 manifest 可以提供来源和展示 metadata，但不能在缺少 `SKILL.md` 时凭空创建 Skill。

Skill 根目录不能嵌套：如果一个已发现 `SKILL.md` 位于另一个 Skill 根目录内部，这组目录范围重叠的 Member 全部验证失败。SkillYard 列出冲突路径，但不根据层级、选择状态或内容推断如何拆分。失败成员不能安装或接管；Source 中其他互不重叠的 Member 仍可用于这些成员级操作。Bundle 更新固定包含 Source 的全部当前成员，因此任一成员涉及该冲突时，整个 Bundle 更新在生效前失败，所有现有受管内容和 Mount 保持不变。

每个 `SKILL.md` 必须包含可解析的 YAML frontmatter，并提供 `name` 与 `description`。`name` 长度为 1–64，只能包含小写 ASCII 字母、数字和连字符，不能以连字符开头或结尾，不能包含连续连字符，并且必须与 Skill 根目录名完全一致；`description` 长度为 1–1024。其他可选或未知 frontmatter 字段原样保留，SkillYard 不评价 Markdown 正文质量。验证失败的 Member 不能安装或接管，界面必须展示具体字段错误；Bundle 更新中任一 Member 验证失败时，整个更新失败并继续使用全部当前受管内容。

同一个 Bundle 内的 Skill Name 必须唯一。不同路径的 Member 如果声明相同 `name`，这些重复成员验证失败，界面只列出重复名称及对应 `SKILL.md` 路径，不提供合并、重命名或覆盖流程。Bundle 更新固定包含全部成员，因此发现任一重复名称时整个更新在生效前失败。不同 Bundle 之间允许同名，由 Bundle 分组和展示标签区分；挂载到同一路径时仍按普通 Mount Conflict 处理。

Bundle 内的 Skill 可以独立挂载，但不能在安装后被单独删除。直接安装时默认选择 Source 中全部已发现成员，用户可以在最终确认前取消部分成员；接管已有安装时，Member Selection 只包含本机原本已经安装并被确认接管的成员。用户主动更新 Bundle 后，Member Selection 改为从关联 Source 获取并通过验证的全部当前成员；此前未安装的成员会被安装，但保持未挂载。

### 更新可控，失败可恢复

SkillYard 1.0 不在应用启动时、后台或定时自动检查上游更新。主界面只提供一个由用户主动触发的“检查更新”按钮；点击后，经过验证的 Adapter 一次检查全部已关联本地 Bundle 且具备可检查上游的 Source，并把结果显示到对应 Bundle 上。检查结果可以是“可更新”“已是最新”或“无法检查”，并可包含上游更新标识和原发布页，但不会获取候选内容、替换当前受管内容或改变任何 Mount。“刷新本机”不能触发这项网络查询。没有关联 Source 的 Bundle 显示“没有更新来源”，不进入检查队列，但仍显示“由 SkillYard 管理”。

GitHub Source 使用最简单的 commit 判定：创建新 Bundle 的首次直接安装保存该 Source 的 Tracked Ref 实际解析出的 commit SHA，后续只有完整 Bundle Update 成功后才推进这条已采用基线；向已有 Bundle 补装成员不推进基线。检查更新时再次解析同一个 ref。SHA 与当前记录不同，关联 Bundle 就显示“可更新”；相同则显示“已是最新”。1.0 不在检查阶段下载仓库、计算 Skill 目录哈希或判断具体哪个成员发生变化。即使新 commit 只修改 README 或未安装成员，Bundle 仍然显示“可更新”。

用户确认切换 Tracked Ref 后，SkillYard 只解析新 ref 的当前 commit 并按同一 SHA 规则更新 Bundle 的检查状态。新 SHA 与上次采用的 commit 不同时显示“可更新”，但不会自动获取候选内容或更新任何 Skill；用户仍需另行发起普通更新。

与已登记 ZIP 或直接文件 Source 关联的 Bundle 没有 Git commit，不参与“检查更新”，界面显示“手动更新”。用户从该 Bundle 进入“导入新内容”，主动选择新的 ZIP 或 `.skill` 文件；SkillYard 将文件放入临时区，重新识别成员并展示影响范围，确认后安装其中全部通过验证的 Skill。它不会在后台访问原 URL，也不使用 `ETag`、`Last-Modified` 或内容哈希自动判断远端变化。没有关联 Source 的 Bundle 不显示这个入口。

检查结果显示在 Bundle 分组标题上；Bundle 中已经安装的 Skill 可以显示“随 Bundle 可更新”，但不会分别发起上游查询。上游新增的成员在更新前显示为“更新后将安装”，不会因为检查动作本身而安装。无法自动检查的 Bundle 保持“手动更新”，不能显示成“已是最新”。

手动提供替换文件仍然是完整的更新能力，因此这类 Skill 可以显示为“由 SkillYard 管理”。`skills.sh` 结果一旦解析为 GitHub Source，就使用 GitHub commit 规则，而不是保留一套 `skills.sh` 更新规则。Editable Local Source 继续使用已经定义的本地修改捕获流程，不属于这里的文件替换更新。

检测到新 commit 或其他上游变化后，界面再提供独立的“更新”动作。只有用户主动执行更新，SkillYard 才会把上游内容获取到临时区、展示完整 Bundle 的安装影响并在确认后替换受管内容。检查更新与执行更新不能由同一个点击静默连续完成。

每个可更新 Bundle 都提供自己的“更新”入口。存在多个可更新 Bundle 时，主界面同时提供“全部更新”；用户点击后，SkillYard 把各 Bundle 分别获取到临时区，并在一个汇总页面展示每个 Bundle 将安装的全部 Skill、现有 Mount 和新增安装。用户可以调整本次参与更新的 Bundle，但不能排除某个参与 Bundle 中的单个 Skill，确认后才执行。

“全部更新”只是批量入口，不把多个 Bundle 合并成一个生命周期事务。每个 Bundle 独立验证、更新和恢复，并按照确认时的顺序逐个执行，不并发修改托管状态；一个 Bundle 失败不阻止后续 Bundle 继续，结束后统一展示成功、失败和未执行结果。每个成功更新的 Bundle 都安装本次获取到的全部有效成员，包括此前未安装或上游新增的成员。

更新确认页保持简单，只展示 Bundle、本次将安装的全部 Skill、其中哪些是新增安装，以及已有 Skill 挂载到的 Supported App 或 Project。GitHub Source 提供“查看上游”链接；没有稳定发布页的手动替换来源不生成虚假的变更说明。页面不展示成员选择、文件列表、文件数量变化、内容 diff、自动提取的 changelog，也不尝试解释 Skill 行为具体发生了什么变化。检测到脚本或可执行文件时仍显示一个简短风险提示，但不把确认页扩展为代码审查工具。

每个 Managed Bundle Directory 只保存一个由 SkillYard 控制的 `current` 软链接。它指向包含该 Bundle 全部已安装成员的完整当前受管内容；每个成员在其中有稳定的受管路径，Host 与 project Mount 指向 `current` 下对应的成员路径。安装、更新和采用 Editable Local Source 修改都先在临时区准备并验证完整候选 Bundle，再通过一次软链接替换原子切换整个 Bundle；现有 Mount 路径不需要改写。

上游更新把关联 Source 的完整当前内容获取到临时区，并把其中全部通过验证的 Skill 与必须保留的上游已移除或不对应成员共同组成一个完整候选 Bundle；用户不能只更新其中一部分。用户确认后，SkillYard 只替换 Bundle 的一个 `current`，所有现有全局和项目级 Mount 同时跟随；此前未安装或上游新增的成员同时进入 Current Content，但保持“已安装、未挂载”，不会自动出现在任何 Supported App 中。更新完成后，本次获取并验证通过的全部成员都加入 Bundle 的 Member Selection；已经安装但上游不再包含的成员仍按既有规则保留。外部工具不能直接覆盖当前受管内容。

Bundle 更新必须先准备完整候选 Bundle，并完成全部成员的结构、名称、Safe Skill Content 和其他既有验证；任何一个成员失败时，整个候选一起废弃，不切换 `current`，也不新增成员。只有全部通过后才能进入生效阶段。替换该 Bundle 唯一的 `current` 就是唯一内容生效点，不存在部分成员先后生效的中间状态。

SkillYard 1.0 不创建本地版本号、版本历史或回滚点，也不提供“使用旧版本”“删除版本”或 Revision 清理入口。事务成功后，旧内容不再作为可选状态保留；只在事务未完成时暂存必要的恢复内容。事务恢复的目标是完成或撤销当前操作，不是让用户在多个版本之间选择。

如果关联 Source 的最新内容已不再包含某个当前已安装的 Skill，SkillYard 保留它的当前受管内容、Member Selection 和 Mount，并标记为“上游已移除”。它不参与这次内容更新，也不会被自动删除；用户可以移除它的 Mount，受管内容则保留到整个 Bundle 被删除。

SkillYard 1.0 不推断成员重命名或路径迁移，也不提供“疑似重命名”确认。名称、路径、描述或内容相似都不能建立身份关联：旧 Skill 按上游已移除成员继续保留，新 Skill 作为本次完整 Bundle Update 的新成员独立安装并保持未挂载。

### 原子生效与中断恢复

每个会修改本地状态的生命周期操作都必须在首次文件系统变更前，同时建立 SQLite 事务记录和持久化的 Filesystem Transaction Journal。Journal 在替换 Bundle 的 `current` 前持久记录旧目标与预期新目标，并保存操作计划、受影响路径、临时恢复内容、持久化阶段以及已经完成的步骤；每一步都必须可以安全地重复执行。启动恢复同时核对 Journal 和实际 `current`：指向旧 Bundle 内容代表生效前，指向新 Bundle 内容代表生效后，指向其他内容则进入人工恢复。SQLite 事务只保护数据库状态，不能代替文件系统事务记录。

用户可以在最终确认前返回、修改选择或放弃计划。最终确认并建立生命周期事务后，操作不允许取消，界面不提供“取消”或“强制停止”入口；离开进度界面也不会终止事务。事务必须运行到成功或明确的阻塞恢复状态。进程意外退出、系统终止或崩溃属于中断，不属于取消，后续启动按 Journal 自动恢复。

SkillYard 1.0 在整个应用中同一时间最多运行一个会改变托管状态的生命周期事务。事务运行期间，其他安装、接管、挂载、更新或删除操作不能建立新事务；对应入口保持不可执行并指向当前操作。“全部更新”由批量协调器按顺序启动各 Bundle 的独立事务，不形成并发写入，也不形成一个跨 Bundle 原子事务。

这一单写限制不锁住整个应用。用户仍可查看已经提交的列表与详情；顶部的当前操作提示始终可见，关闭进度页或切换到其他页面不会影响事务。受影响数据在事务完成前只显示进行中状态，不把文件系统中间步骤当作已经完成的管理状态。

应用启动时优先检查未完成事务：

- 在 Bundle `current` 生效点之前中断：保留原有完整 Bundle 和 Mount，清理候选内容；
- 在 Bundle `current` 生效点之后中断：保留新的完整 Bundle，并继续完成 Mount、SQLite 记录、验证和清理；
- 接管、Cascading Delete、移除 Project 等多路径操作：根据持久化阶段从最后一个已完成步骤继续，每一步重复执行仍得到同一结果。

正常中断不要求用户选择任何内容状态；自动恢复成功后只提示“已恢复上次中断的操作”。只有托管内容缺失、目标路径被外部修改、权限异常或其他证据不足以安全判断目标状态时，SkillYard 才阻塞相关 Skill 的写操作并显示人工恢复页面；不相关的 Skill 仍可正常使用。

### 移除 Mount、删除 Bundle 与删除 Source 是三种操作

移除 Mount 只停止 Skill 在所选 Supported App 或 Project 中的使用，不删除 Member Selection、所在 Managed Bundle Directory 或当前受管内容。用户既可以移除单个 Mount，也可以从 Bundle 卡片一次解除该 Bundle 的全部 global 和 project Mount；后一种操作使用普通影响预览和同一套可恢复 Removal 事务，完成后整个 Bundle 保持“已安装、未挂载”，Source 与更新能力不变。1.0 没有“卸载 Skill”“删除 Skill”或选择部分成员删除的入口。

删除 Bundle 是删除本地已安装组。它会移除该 Bundle 下全部 Skill 的 global 和 project Mount、Member Selection、Managed Bundle Directory、当前受管内容和 Bundle 记录，但保留关联 Source。删除完成后，用户仍可在 Source 页面重新安装这些 Skill。该操作属于 Cascading Delete。

删除 Source 是删除上游来源记录。它会移除该 Source 的成员目录、检查结果、更新标识以及与 Bundle 的更新关联，但不会删除任何本地 Bundle、Skill、Mount、Member Selection、Managed Bundle Directory 或当前受管内容。关联 Bundle 继续显示“由 SkillYard 管理”，更新状态改为“没有更新来源”，所有更新入口不可用；用户重新添加并关联 Source 后可以恢复更新能力。删除 Source 不属于 Cascading Delete。

SkillYard 1.0 不提供把一个已关联 Source 的 Bundle 直接“更换来源”的入口。用户希望改用另一个 canonical Source 时，必须先删除旧 Source，使 Bundle 进入“没有更新来源”状态，再添加并按普通来源关联流程关联新 Source；若新 Source 已经关联另一个 Bundle，则继续使用既有归并流程。两步之间不会改变当前受管内容或 Mount，也不会自动执行更新。修改同一个 Source 的 Tracked Ref，或为 Unavailable Editable Local Source 重新指定路径，仍属于 Source 维护，不是更换 Source。

四个初始推荐来源没有特殊删除保护。用户删除后，它们与普通 Source 一样从本地来源列表消失；需要再次使用时，可以按普通添加来源流程重新添加。1.0 不提供停用状态或“恢复默认来源”入口。

删除 Bundle 的 Cascading Delete 必须经过两次确认。第一次展示全部受影响 Skill、Supported App、Project、Mount 和将永久删除的受管内容；第二次明确说明这是危险的级联删除，并再次要求用户确认。成功后没有回滚入口。删除只作用于 SkillYard 管理的本地内容和 Bundle 记录，不删除保留的 Source、GitHub 上游、用户拥有的 Editable Local Source 目录、Agent 应用管理内容或项目仓库管理内容。

删除 Source 只需普通确认，并明确提示哪些现有 Bundle 将失去更新来源；它不能复用删除 Bundle 的危险文案，因为本地受管内容不会被删除。

### 管理状态是一份完整承诺

只要一个 Skill 已经进入 SkillYard 创建或接管的本地 Bundle，其当前受管内容、Mount 和 Bundle 删除都由 SkillYard 控制，界面就显示“由 SkillYard 管理”。更新能力来自可选的 Source 关联，是独立状态，不能反过来决定管理归属。Bundle 负责组织本地安装与删除范围；Source 负责发现和更新。

“上游已移除”是来源成员状态，不是管理权状态。它可以被移除 Mount，但受管内容只随 Bundle 删除。

“来源不可用”同样是 Source 可用性状态，不是管理权状态。只要当前受管内容仍完整，相关 Skill 继续显示为“由 SkillYard 管理”。

## 保留原管理方的例外

以下内容只读展示，不强行接管：

- Codex 插件或其他 Host 随应用提供的 Skill；
- Host 内置 Skill；
- 明确由项目 Git 仓库维护的 Skill。

SkillYard 展示它们的来源和位置，并把生命周期操作交回 Codex、对应 Host 或项目仓库。1.0 从 `~/.codex/plugins/cache/openai-primary-runtime`、`~/.codex/plugins/cache/openai-bundled` 和 `~/.codex/plugins/cache/openai-curated-remote` 三个 Codex 官方缓存根中读取插件；同一插件只展示最近的缓存版本，插件名作为只读 Bundle 分组名称，其中的 Skill 可以逐个进入详情。SkillYard 不修改这些缓存，也不提供安装、更新、挂载或删除操作。

Codex 或其他 Agent 应用如何为 Skill 添加目录、插件或分组前缀，属于对应 Host 的展示设计。SkillYard 可以只读展示该 Host 实际使用的标签，但不得把它写回为 Skill Name，或据此修改受管内容、Mount 和身份记录。

同一 Skill 即使被多个 Host 以不同标签展示，在 SkillYard 主列表中仍使用同一个 SkillYard Presentation Label；Host 差异只出现在对应的使用关系和详情中。

## 外部工具的角色

`npx skills`、`gh skill`、Lark CLI 等工具在 1.0 中只作为外部 Installation Chain 和来源证据。用户可以在 SkillYard 之外运行它们；SkillYard 随后通过“刷新本机”扫描安装结果并生成接管计划。

1.0 自动读取的外部安装收据只限已经核验的 lock v3。它保存 lock 记录位置、Source URL／路径、上游 Skill 路径、ref、内容 marker 和时间，但不能据此判断记录由 `skills`、`gh skill` 还是 Lark CLI 写入。Lark 专属状态、GitHub frontmatter 和其他 receipt／manifest 格式留到后续版本；扫描阶段只把 lock 来源作为接管证据，用户确认接管后才按上述规则创建或复用可更新的 Source。

SkillYard 1.0 不执行这些命令来安装或更新 Skill。内容接管后，由 SkillYard 维护当前受管内容、执行更新、管理 Mount，并在删除 Bundle 时移除受管内容；外部命令不得直接修改受管主副本。

## 不内置 LLM

SkillYard 1.0 不捆绑或下载本地 LLM，也不调用云端模型。扫描、Source 恢复、Bundle 与 Skill Identity 判断、安装、更新、接管计划和文件操作全部依赖确定性的本地证据、受支持 Adapter 和用户明确确认。

证据不足时，界面显示“来源未知”并保留已经确认的位置、内容和安装线索；SkillYard 不使用模型猜测 Source、发布者、安装命令、Skill Identity 或可下载文件。解释 Skill 和辅助调查来源可以在后续版本作为可选能力重新讨论，但不属于 1.0 产品或运行依赖。

### 来源未知仍可接管

Unknown Provenance 不阻止 Takeover。只要 Skill 的本地内容边界能够确认，用户就可以审核接管计划，把当前内容保存为受管主副本，并由 SkillYard 负责当前内容、Mount 和 Bundle 删除。它仍显示“由 SkillYard 管理”，同时独立显示“来源未知”与“没有更新来源”；用户之后补充 Source 关联后再获得更新能力。

用户以后找到真实 GitHub 或其他 Source 时，可以发起“补充来源”。GitHub 仓库始终登记为完整 Source；对每个本地 Skill，用户只需选择它是否“对应”该 Source 当前的某个 Skill。选择“对应”时再指定成员；选择“不对应”时不记录它是被删除、本地改造还是其他原因。Source 已经关联另一个 Bundle 时，“补充来源”同时进入上述归并计划，不能建立第二条关联。

来源关联不会覆盖当前受管内容或重置 Mount。关联成功后，整个 Bundle 获得 Source-backed 更新路径；“对应”只建立本地 Skill 与当前 Source Member 的身份连续性，“不对应”不建立成员映射。仓库其他成员在关联时只显示为可用，不自动安装；用户之后更新该 Bundle 时，按完整 Bundle 更新规则安装全部当前 Source 成员，并把“不对应”和上游已移除的既有成员保留在新的完整 Bundle 中。

对于选择“对应”的 Skill，SkillYard 不通过内容相似度反查当前本地内容对应的历史 commit，也不附加猜测的 SHA。关联完成后，所跟踪 ref 的当前 commit 直接显示为“可更新”。只有用户主动完成第一次更新后，SkillYard 才把该 commit 记录为已采用的上游基线，此后再按普通 commit SHA 规则检查更新。

## 本地数据边界

SkillYard 使用本地 SQLite 分别记录 Source 与 Bundle，并保存两者可选且唯一的一对一更新关联。SQLite 还记录首次扫描状态、最近一次“刷新本机”的时间与结果、Inventory、Skill Member、Skill Identity、Member Selection、成员可用性、每个 Source 上次成功成员目录、成功获取时间与最近重新加载结果、每个 Bundle 的当前内容引用和预期 `current` 目标、每个 Skill 的稳定受管成员路径、已采用的上游更新标识、项目使用关系、Mount 和生命周期事务。Skill 内容、Bundle `current`、临时恢复内容以及每个未完成操作的 Filesystem Transaction Journal 保存在本地文件系统中；SQLite 记录引用并核对这些 Journal，但不能替代它们。SQLite 不保存本地版本历史或回滚点。

1.0 不依赖 SkillYard 自建账号体系、云端数据库或公共 registry 才能完成核心流程。

SkillYard 1.0 采用 Zero Telemetry：不收集或上传使用分析、设备或用户标识、崩溃与错误报告，也不上传 Skill 名称、Source URL、Project 或 Host 路径、文件名、Inventory、SQLite 状态等本机管理信息。macOS 自己生成的崩溃报告保持在本机，SkillYard 不主动读取或上传。用户明确触发 Source 获取、目录或搜索加载、Update Check 和 Bundle Update 时可以发起完成该动作所必需的网络请求，但请求不能附带分析事件或遥测标识。

SQLite 生命周期状态和 Filesystem Transaction Journal 只服务于本机一致性与中断恢复，不属于遥测。由于 1.0 不存在遥测，界面也不需要提供遥测同意、退出或隐私开关。

macOS 1.0 的 SkillYard-managed Mount 使用软链接，不静默退化为复制。复制会产生独立实体副本，破坏“一处更新、所有挂载同步”的管理承诺。

### 删除应用本体不删除 Skill

用户把 `SkillYard.app` 拖进废纸篓、替换应用版本或暂时移除应用本体时，SkillYard 不删除任何 Skill 受管内容，也不删除 Central Store。已经存在的 Host 与 project Mount 继续通过各 Bundle 的 `current` 访问对应成员，因此 Agent 应用中的 Skill 仍可使用；不需要在删除应用前把软链接转换成普通文件，也不能依赖用户提前执行准备操作。

用户安装新版并手动替换 SkillYard 后，应用检测固定位置中的现有 SQLite 和文件系统状态，完成必要的未结束事务恢复后继续管理原有 Skill。删除 `.app` 不能被解释为删除本地数据或撤销 Local Lifecycle Authority。

“重置应用”只能清除偏好设置、窗口状态和缓存。它不能删除或重建 SQLite、Central Store、当前受管内容、`current`、Mount、Member Selection 或生命周期事务记录；重置后仍应从原有托管状态继续工作。

SkillYard 1.0 不提供“彻底清除 SkillYard”或一次性移除全部托管内容与 Mount 的功能。完整移除流程留给后续版本专门设计，不能通过删除应用、重置设置或手动清理 Central Store 来代替。

### 1.0 不提供备份与恢复

SkillYard 1.0 不提供 Central Store 的手动导出、备份文件、从备份恢复、自动备份、云备份、定时备份或跨设备迁移。系统级或用户自行执行的目录备份不属于 SkillYard 1.0 的产品承诺，界面不能把未经验证的目录复制描述成可恢复备份。

这项范围不影响生命周期事务恢复和接管过程中的临时恢复内容；这些机制仍是本机安全操作的一部分，但不能被包装成面向用户的完整备份与恢复。Central Store 仍然是持久用户内容和已接管 Skill 的唯一主副本，备份与恢复将在后续版本单独设计。
