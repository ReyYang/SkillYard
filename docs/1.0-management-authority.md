# SkillYard 1.0 接管与管理权设计

> 本文件细化 [1.0 产品契约](1.0-product-contract.md)的本地数据、文件、事务和界面规则；如两者冲突，以产品契约为准。完整文档层级见 [文档索引](README.md)。

## 已确认原则

SkillYard 1.0 采用“一律接管、按需搬迁”。

只要用户希望把一份 Skill 交给 SkillYard 管理，SkillYard 最终就必须统一负责它的当前主副本、挂载和 Bundle 删除。整个仓库或完整上游登记为 Source；用户确认直接安装或接管已有内容时，SkillYard 才创建本地 Bundle。接管时保留本机已有的部分安装状态；Bundle 关联 Source 时，用户主动更新会安装该 Source 中的全部有效 Skill。来源工具、安装命令和发布者仍作为来源与安装履历保存，但不再控制正在使用的本地副本。

这意味着“由 SkillYard 管理”描述的是本地管理权：凡是位于 SkillYard 创建或接管的 Bundle 中的 Skill，其当前受管内容、Mount 和 Bundle 删除都由 SkillYard 控制。Source 只决定是否具备上游发现和更新能力；Source 被删除或暂时不可用时，Bundle 仍由 SkillYard 管理。只读 Inventory 条目不能显示为“由 SkillYard 管理”。

Bundle 是本地已安装组和删除范围；Source 是上游目录与更新入口；Skill 仍是挂载单位。直接安装时默认选择 Source 的全部成员，接管已有安装时保留已有成员集合。一次 Bundle 更新固定安装从关联 Source 获取并通过验证的全部成员，不提供成员排除，也不产生本地版本历史或回滚点。1.0 不提供单独卸载或删除 Skill Member 的入口。

1.0 的范围以完整主流程为筛选标准，而不是以功能数量为目标。首次扫描与 Inventory、直接安装或接管、Bundle／Skill 查看、Mount 管理、Source 关联与检查、完整 Bundle 更新、Source 删除、Bundle 删除和中断恢复必须真正可用；只服务于外围便利性的功能后置。确认、候选内容验证、原子生效、事务恢复和管理权隔离属于主流程成立的条件，不能为了减少界面或状态而省略。

## 1.0 应用架构

SkillYard 1.0 采用 Tauri 2、TypeScript Web UI 与 Rust Lifecycle Core。本机应用把前端静态资源打包进 `.app`，由 macOS 系统 WKWebView 加载，不运行 localhost Server，也不携带 Chromium、Python runtime 或 Python sidecar。旧 Python CLI、HTML View 和 Local Server 已从当前工作区删除，不构成 1.0 runtime dependency 或产品入口。

TypeScript 层负责界面渲染、临时交互状态、用户选择和确认呈现。它只能调用面向产品动作的类型化命令，例如读取 Inventory、生成 Plan、执行已确认事务和读取恢复状态；不能直接读取或修改 SQLite、Central Store、Host 路径、Project 路径或 Filesystem Transaction Journal，也不能执行 shell。

Rust Lifecycle Core 是唯一的本机管理权执行边界，负责 SQLite、Source Adapter 网络请求、本地扫描、路径与 Safe Skill Content 验证、Bundle 候选内容、软链接以及事务生效与恢复。前端不能获得通用 `fs`、`sql` 或 `shell` plugin 权限；Tauri capability 只允许调用经过定义的 SkillYard 业务命令。这样可以让 Web UI 保持易于维护，同时不把高风险文件权限扩散到展示层。

`SkillYard.app` 是 1.0 唯一的用户入口。应用不通过 HTTP API 连接自身，也不提供 CLI、headless 模式、独立 daemon、localhost API、公开 Rust API 或单独安装的恢复工具。Lifecycle Core 仅作为 `.app` 内部模块存在，不为未来 CLI、插件或自动化预先建设稳定接口；测试直接调用内部模块不构成第二个产品入口。

因此，所有支持的扫描、安装、接管、Mount 管理、更新、删除和中断恢复流程都必须在 App 内可完成。1.0 不能把失败恢复说明改成要求用户运行命令，也不能把 Agent 指令、开发测试 harness 或 Central Store 中的说明文件描述成正式操作入口。后续若增加第二个入口，需要新的产品决策和独立授权边界。

## macOS 本机运行与权限模型

SkillYard 1.0 只在产品所有者的个人 Mac 上本地构建和运行，不制作面向其他用户的 DMG、ZIP、GitHub Release 或其他安装包。1.0 不加入 Apple Developer Program，不承诺 Developer ID、Hardened Runtime、Apple notarization、stapling 或无警告的 Gatekeeper 安装体验；本地构建可以使用 macOS 或 Tauri 所需的 ad-hoc signing，但它不代表 Apple 验证身份。

Supported Platform 固定为 Apple Silicon（`arm64`）与 macOS 14 Sonoma 及以上。本机构建与验收只处理 `arm64`，`LSMinimumSystemVersion` 或等价部署目标固定为 `14.0`。1.0 不产出 Intel（`x86_64`）或 Universal 2 artifact，不把 Rosetta 当作支持路径，也不接受只在未列入矩阵的系统上“碰巧运行”作为兼容性承诺。

不启用 App Sandbox 是本地管理模型的一部分。SkillYard 需要持续读取已确认的 Supported App 路径、Project 路径和固定 Central Store，并在生命周期事务中创建目录、移动受管内容、原子替换 `current` 和维护 Mount。1.0 不把这些目录迁入 `~/Library/Containers`，也不把首次扫描改成逐个目录的 security-scoped bookmark 授权流程。

每次扫描与写事务都以当前登录用户身份运行，并在计划阶段检查目标路径的实际可读写性；TCC、POSIX permission、ACL、System Integrity Protection 或只读文件系统拒绝访问时，操作必须在首次变更前失败。SkillYard 不提权，也不绕过系统保护。

1.0 不提供 Application Update、更新源、下载安装器或 GitHub Releases 发布流程。需要更新应用本体时，产品所有者在同一台 Mac 上重新构建并手动替换 `SkillYard.app`。手动替换不能读取、迁移或删除 SQLite、Central Store、Current Content、Filesystem Transaction Journal 或 Mount；新构建启动后仍先执行普通事务恢复。

因此，1.0 界面中的“检查更新”和 Bundle Update 只指 Skill Source 内容，不能被解释为检查或替换 `SkillYard.app`。公开分发和 Application Update 留到后续确实需要其他用户安装时再单独设计。

## 四种界面状态

| 状态 | 含义 | SkillYard 行为 |
| --- | --- | --- |
| 由 SkillYard 管理 | Skill 已进入 SkillYard 创建或接管的本地 Bundle | 管理当前内容与挂载，并可随 Bundle 删除；关联 Source 时还可更新 |
| 待接管 | 已发现且可能接管，但用户尚未确认接管计划 | 只读扫描、解释来源并生成接管计划 |
| Agent 应用管理 | Codex 插件、应用内置或应用包内的 Skill | 只读展示，并跳转到原管理方 |
| 项目仓库管理 | 明确由项目 Git 仓库维护的 Skill | 只读展示，并跳转到对应项目 |

“来自外部工具”不是第五种长期管理状态。`npx skills`、`gh skill`、Lark CLI 或其他工具安装出来的内容，在接管前可以是待接管对象；接管后，这些工具只保留为 Installation Chain 和来源证据。SkillYard 1.0 不执行它们来安装或更新 Skill。

“已安装、未挂载”也不是第五种管理权状态，而是“由 SkillYard 管理”之下的一种使用状态。此时 Skill 已存在于 Bundle 的 Managed Bundle Directory 和 Member Selection 中，但没有 Mount，因此不会通过 SkillYard 暴露给任何 Host。重新挂载能力保持不变；Bundle 有关联 Source 时才能更新，没有 Source 时不能更新，受管内容只随 Bundle 删除。

## Supported App 由 SkillYard 内建维护

SkillYard 1.0 的 Supported App 表固定包含 Codex、Claude Code 和 GitHub Copilot。每个应用配置记录显示名称、固定的应用专属 global Mount 根目录、固定的应用专属 project Mount 根目录、只读兼容目录、已知路径重叠关系，以及可选的安装检测方式。Cursor、Gemini CLI 和其他 Agent 应用不属于 1.0 Supported App 表，因此不能成为 SkillYard-managed Mount 的目标。

| Supported App | global Mount 根目录 | project Mount 根目录 |
| --- | --- | --- |
| Codex | `~/.codex/skills` | `<project>/.codex/skills` |
| Claude Code | `~/.claude/skills` | `<project>/.claude/skills` |
| GitHub Copilot | `~/.copilot/skills` | `<project>/.github/skills` |

多数应用只需要内建的路径配置，只有少数路径结构、只读边界或安装识别方式特殊的应用才需要专门逻辑。安装检测只产生“已检测到”或“未检测到”状态，不会生成应用配置，也不改变 Supported App 表。发现一个包含 `SKILL.md` 的未知目录、相似路径或新的 Agent 应用，不能让它成为可选挂载目标。

同一个应用的多个有效目录由一份配置在内部处理，界面仍然只显示一个应用复选项。只有用户确实需要把两个目标分别勾选或取消时，SkillYard 才把它们定义为两个 Supported App。1.0 不引入 Host Family、Runtime Surface 或品牌层级。

“支持某应用”只表示 SkillYard 能正确扫描并管理它的本地 Skill 目录，不延伸为对该品牌全部云端、IDE、插件或其他能力的承诺。用户勾选一个 Supported App，表示授权 SkillYard 向上表中该应用的固定路径写入 Mount，而不是要求 Skill 只能被这个应用发现。目标路径如果也被其他 Supported App 兼容扫描，影响预览必须列出可能同时发现该 Skill 的应用。1.0 不写入或调用其他 Agent 的 enable／disable 配置来制造独占可见性。

## 首次使用与后续启动

SkillYard 以 SQLite 中明确的首次扫描完成记录判断是否进入介绍页，而不是以本机是否可能存在 Skill 来猜测。没有完成记录时，应用只展示首次使用说明和“开始扫描”按钮；用户点击前不读取 Supported App 的 Skill 目录。

用户点击“开始扫描”后，SkillYard 执行一次本地只读盘点，保存完成记录和发现结果，再进入正常 Skill 列表。扫描结果为空也算完成，不能因此在下次启动重复要求用户扫描。首次盘点只建立 Inventory 和管理方分类，不授予 Takeover 权限，也不创建 Managed Bundle Directory、受管内容或 Mount。

已有首次扫描完成记录时，应用启动后先读取 SQLite 中的未完成事务并执行恢复，再对已有 Mount 执行只读的本地健康检查，最后展示此前发现、配置和选择的 Skill。启动不会再次显示首次使用介绍页，也不会检查上游更新。

## “刷新本机”与“检查更新”

“刷新本机”是用户主动触发的本地只读盘点。它重新扫描 Codex、Claude Code 和 GitHub Copilot 配置中的 global、project 和只读证据目录，以及 SQLite 中已登记 Project 的对应 Skill 目录；同时重新读取收据、lock 文件和其他本地 Management Evidence，并检查已有 Mount 的健康状态。

这次扫描可以发现用户在 SkillYard 外通过 `npx skills`、`gh skill`、Lark CLI、本地复制或其他方式新增、移除或改变的 Skill。结果只更新 Inventory、Management Evidence 和 Mount 健康状态；它不能联网、自动接管、搬迁、安装、删除受管内容、修复 Mount 或改变 Local Lifecycle Authority。

“检查更新”是另一个由用户主动触发的只读动作。它只查询已登记 Source 的上游状态，不重新扫描本机安装目录。应用启动只恢复未完成事务并执行已登记 Mount 的轻量健康检查，不自动执行完整的“刷新本机”或“检查更新”。

## 主界面信息架构

SkillYard 主界面第一层是 Bundle／管理分组列表，不直接平铺全部 Skill。受管 Bundle 卡片使用 Bundle Display Name，展示成员数量、更新状态和 Bundle 级操作；进入 Bundle 后显示成员列表，进入成员后显示来源、路径、Metadata、安装收据和零个或多个 Supported App／Project Mount。每个 Skill Identity 只在所属 Bundle 详情中出现一次。

Bundle 标题只代表本地已安装组。`.agents/.skill-lock.json` 提供确定性 GitHub 安装收据时，规范化 `sourceUrl` 决定 Bundle 身份，`source` 决定 Bundle Display Name；可选 `pluginName` 不参与拆分或命名。若 Bundle 仍关联 Source，可以同时提示该 Source 中尚未安装的可用 Skill 数量；完整上游目录在 Source 或关联详情中展示，不因此成为本地 Bundle 成员。Bundle 提供安装、批量入口与影响预览，但自身不拥有统一的 Mount。同一 Bundle 中的 Skill 可以分别挂载，但不能单独删除；更新以 Bundle 为执行范围，并会安装从关联 Source 获取到的全部有效成员。

待接管条目只在确定性安装证据相同时组成一个待接管 Bundle；没有证据时保持独立的一成员候选。Agent 应用管理与项目仓库管理的 Skill 不创建 Bundle，而是按原管理方或项目形成只读导航分组。Supported App 与 Project 不能各自复制一套 Skill 清单；同一 Skill 的全部使用关系归属于同一个详情页。

默认视图覆盖 Inventory 中本机已有或已经安装的全部 Skill，但第一层只展示 Bundle／管理分组。仅在上游 Source 目录中发现、但尚未安装或出现在本机的成员不进入主列表。界面提供“全部”“由 SkillYard 管理”“待接管”和“其他管理方”等管理状态筛选；“其他管理方”包含 Agent 应用管理与项目仓库管理。搜索命中成员时保留所属分组卡片，不恢复平铺 Skill。筛选与搜索只改变展示，不写入管理权或生命周期状态。

主界面常驻操作用于检查更新、安装、添加项目和刷新本机。低频维护动作“重置应用”和“打开 Central Store”统一放在设置页；移动入口不改变两项操作既有的非破坏性边界。

一个生命周期事务运行时，用户仍可浏览、搜索、筛选和打开其他 Bundle、Skill、Supported App 与 Project 详情。全局顶部区域持续展示当前操作，并可返回进度页；本次受影响的条目显示“处理中”，不暴露文件系统中间状态。所有会持久化新状态的入口暂时不可执行，包括“刷新本机”“检查更新”、发现页重新加载、安装、接管、挂载、更新、Project 移除和 Cascading Delete。事务结束后，界面从最终持久化状态刷新并恢复可用入口。

## Skill 名称与 Host 展示标签

Skill Name 来自 Skill 内容本身。Host Presentation Label 由 Codex 或其他 Agent 应用为自己的界面生成，可以把插件名、Bundle 名或目录分组作为前缀带上。

```text
Skill Name: qa
Host Presentation Label: Mattpocock Skills: Qa
```

这不是 Skill 重命名。SkillYard 可以在对应 Host 的使用关系中只读展示该标签，但不能把前缀写回 Skill Name，也不能把 Host Presentation Label 当作 Skill Identity、Source、Bundle 或 Mount 名称的直接证据。Host 如何生成或修改标签，仍由 Host 自己管理。

SkillYard 自己拥有独立的 SkillYard Presentation Label，统一采用以下组合：

```text
SkillYard Presentation Label: mattpocock/skills: qa
Bundle Display Name: mattpocock/skills
Skill Name: qa

Codex Host Presentation Label: Mattpocock Skills: Qa
```

列表和搜索结果使用 SkillYard Presentation Label；详情页把 Bundle Display Name、Skill Name 和每个 Host Presentation Label 分开显示。同一 Skill 挂载到多个 Host 时，Host 标签可以不同，但 SkillYard Presentation Label 保持一致。所有这些标签都属于展示层，不参与 Skill Identity、更新或挂载判断。

Bundle Display Name 在 Bundle 创建时固定为来源输入的稳定名称：GitHub 仓库使用 canonical `owner/repository`，其余来源使用 package name，或 ZIP、本地目录的 basename。Source 后续被删除时名称继续保留。1.0 不提供自定义名称，也不为这个字段建立额外的推断和优先级系统。

Mount 的目标根目录由 Host 与 scope 决定，叶子目录名固定使用 Skill Name。例如 `Skill Name: qa` 对应的软链接目录名就是 `qa`。Bundle 前缀、SkillYard Presentation Label 和 Host Presentation Label 都不会进入文件系统路径；1.0 不支持 Mount alias、自动后缀或自定义目录名。同名路径已存在时按 Mount Conflict 处理。

## 接管事务

接管必须按以下流程执行，不能在扫描时静默移动文件：

```text
扫描
  → 接管计划
  → 用户确认
  → 备份
  → 必要时搬迁
  → 替换或校正软链接
  → 验证
```

### 1. 扫描

扫描只读取目录、文件、软链接、Git 信息、已核验的 lock v3、来源 metadata 和已知 Host 配置。它用于识别 Skill 边界、候选 Source、将由接管创建的本地 Bundle、现有使用位置与潜在冲突，不改变任何安装。用户确认接管后，能够规范化为 GitHub 仓库的 lock v3 来源在同一接管提交中创建或复用 Source，并关联该 Bundle；扫描本身仍不写入。1.0 不解析 Lark 专属状态、GitHub frontmatter 或其他 receipt／manifest 格式。

### 2. 接管计划

计划必须明确展示：

- 将要创建或补充的本地 Bundle、可确认的 Source 以及已发现成员；
- 用户将接管的 Skill Member 及保存后的 Member Selection；
- 当前主副本候选与来源证据；
- 哪些路径保持原位，哪些路径需要搬迁；
- 哪些 Host 或项目路径会被替换为软链接；
- 多应用共享目录会写入哪些实际 Mount 路径，以及哪些 Supported App 可能同时扫描这些路径；
- 会创建的临时恢复内容、受管主副本和挂载；
- 冲突、失效链接、重复副本及预计影响。

### 3. 用户确认

确认对象是这份具体计划，而不是笼统授权 SkillYard 扫描后自行整理磁盘。计划发生变化时必须重新确认。

### 4. 事务恢复临时内容

任何移动、替换或删除前，事务都要临时保留足以在操作失败时恢复原目录结构和原文件内容的数据。它只服务于当前事务的安全恢复，不是用户备份、可选版本或回滚点；事务验证成功后立即清理。

### 5. 按需搬迁

- 如果内容已经位于符合 Central Store 规则的 Managed Bundle Directory，不做无意义搬运，只创建或补充 Bundle、登记可确认的 Source 关联、准备完整候选 Bundle，并校正挂载关系。
- 如果内容散落在其他位置，则把选中内容与 Bundle 已有成员共同准备为完整候选 Bundle，迁入 Central Store，并通过该 Bundle 唯一的 `current` 一次生效；原使用位置替换为指向 `current` 下稳定成员路径的软链接 Mount。
- Codex 插件、Host 内置 Skill 和明确由项目仓库维护的 Skill 不进入该流程。

接管已有安装时，Bundle 只记录用户确认接管的本地 Skill，并把它们加入 Member Selection；已核验的 GitHub lock v3 能确认上游时，接管事务自动建立 Source 关联并保存可确认的成员路径。每个已选 Skill 可以分别拥有全局或项目级 Mount；Source 中其他成员保持可用状态，不被搬迁或挂载。

接管计划的默认勾选范围必须来自扫描到的现有安装，不能因为找到了对应的完整 Bundle 就把其他成员预选或安装。用户确认前，这些默认值只是计划，不是持久化状态。

来源未知的多个不同 Skill 只有在确定性 Management Evidence 证明它们来自同一安装组时，才能在一份接管计划中组成同一个 Bundle。可采用的证据包括 receipt、lock、安装 manifest、经过核验的 Adapter 结果或其他能够直接表达安装组边界的记录。共同位于一个 Supported App Skill 根目录、共享父目录、名称相似或位置相邻都不够；没有安装组证据时，每个 Skill 各自创建一个 Bundle。影响预览必须明确展示这一边界，因为 Bundle 决定唯一的 `current`、更新范围和 Cascading Delete 范围。

扫描到的每个现有 Host 使用位置都属于接管计划的输入。事务把选中内容写入 Managed Bundle Directory 的完整候选 Bundle，验证后建立或替换该 Bundle 唯一的 `current`，再在原路径创建指向对应稳定成员路径的软链接 Mount，从而保持接管前已经可用的 Host 关系。用户可以在影响预览中取消某个 Mount，但默认不要求重新选择已有 Host。

#### 重复副本

当确定性证据表明多个本地安装属于同一个 Skill 时，接管后只能保留一个主副本：

- 内容完全相同时，接管计划可以直接把它们合并为一个待接管 Skill，并保留扫描到的全部现有使用位置；
- 内容不同时，用户必须选择其中一份内容，影响预览必须明确说明其他副本将被替换；
- 只有用户选中的副本会作为该成员内容进入完整候选 Bundle；Bundle `current` 生效后，所有现有使用位置都改为指向该成员的稳定受管路径；
- 接管计划不能让某个位置继续保留未选中的副本；用户不接受全部位置统一时，只能取消这次接管；
- 未选中的内容只在事务执行期间作为临时恢复内容保存，验证成功后清理，不形成可选旧版；
- 用户未完成选择或取消接管时，不移动、替换或删除任何副本。

本地内容比较只用于处理这次重复副本冲突，不参与 GitHub Bundle 的更新判断；GitHub 更新仍只比较已记录 commit 与当前 commit。

#### 用户确认同名副本身份

相同 Skill Name 只能形成待确认候选，不能成为自动合并的证据。当多个来源未知的本地副本同名，但没有确定性 Management Evidence 证明其身份相同时，SkillYard 可以让用户明确确认“它们是同一个 Skill”。

确认后，SkillYard 为这些副本建立同一个本地 Skill Identity，并继续执行重复副本流程：内容不同时选择唯一主副本，随后让全部现有位置使用同一份当前受管内容；如果还存在 global 与 project 并存，再完成 scope 选择。用户不确认时，各副本保持独立，SkillYard 不搬迁、替换或合并它们。

这项人工确认只解决本地身份，不建立或猜测 Source、Bundle Member、上游 commit 或发布者。相关 Bundle 继续显示 Unknown Provenance 和“没有更新来源”，所有更新入口不可用；只有用户另外关联 Source 后才能更新。

#### 接管时的 scope 冲突

如果同一个 Skill 在同一个 Supported App 中已经同时存在 global 和 project 安装，接管计划必须让用户选择一种 Mount Scope：

- 选择 global：保留或创建一个 global Mount，移除扫描到的 project 副本，相关项目之后通过 global Mount 使用该 Skill；
- 选择 project：移除 global 副本，并把扫描到的全部项目位置改为指向同一稳定成员路径的 project Mount；
- 如果各处内容不同，用户仍按重复副本规则选择唯一主副本；内容选择与 scope 选择都完成后才能执行事务；
- 用户未完成选择或取消时，不修改任何现有安装。

这是接管已有非托管安装时为消除既有 Scope Conflict 提供的事务选择，不代表普通挂载操作可以自动在 global 与 project 之间转换。

#### 多应用共享目录

`~/.agents/skills` 和项目 `.agents/skills` 等被多个 Agent 应用共同扫描的目录不能证明用户希望保留哪些应用关系，也不能成为 SkillYard 新 Mount 的目标。接管计划必须明确列出会读取该共享目录的已知 Supported App，并由用户选择希望 SkillYard 为哪些应用维护 Mount 关系；事务一律迁往上表中对应的应用专属路径。如果专属目标仍被其他应用兼容扫描，影响预览必须同时说明交叉可见性。移除原共享入口还可能使 Supported App 表之外的其他应用不再发现该 Skill，也必须提示。

事务按以下顺序执行：

```text
扫描共享目录中的已有 Skill
  → 用户选择希望由 SkillYard 维护 Mount 关系的 Supported App
  → 展示每个选择的实际目标路径与交叉可见性
  → 备份原共享入口
  → 登记或迁移主副本到 Managed Bundle Directory
  → 验证完整候选 Bundle 并建立或替换唯一 current
  → 在所选应用的固定专属路径创建指向稳定成员路径的 Mount
  → 验证每个所选应用可以发现 Skill
  → 全部成功后移除或替换原共享入口
```

共享入口移除前不能把事务标记为成功。任一目标 Mount 创建或验证失败时，SkillYard 必须删除本次新增 Mount、恢复原共享入口并保留失败记录，不能留下共享入口与部分新 Mount 混用的中间状态。Supported App 的选择只表达 SkillYard 的写入和记录意图，不保证未选择的应用无法兼容扫描专属路径。

### 6. 验证

至少验证完整 Bundle 受管内容、Bundle `current` 的目标、Mount 指向 `current` 下正确的稳定成员路径、原使用方仍能发现 Skill、SQLite 记录与文件系统一致。任一步失败都按持久化阶段恢复或完成事务。

## 安装与更新

SkillYard 1.0 必须提供安装能力。受支持的入口包括：

- GitHub 仓库或明确的 GitHub 路径；
- `skills.sh` 提供的来源；
- URL；
- ZIP；
- 本地目录。

通用 URL 入口不等于网页抓取器。1.0 只接受以下可确定解析的地址：

- 公开 GitHub 仓库或成员路径；
- 可直接下载的 ZIP 或 `.skill` 文件；
- 已有 Adapter 明确支持的官方 Skill index 或 manifest。

普通 HTML 页面、推特、知乎、论坛帖子和其他内容页面只能作为用户自行查看的发布页，不能直接进入安装事务。SkillYard 不抓取页面寻找链接，也不使用 AI 推断哪个附件、代码块或命令代表真实 Source。

### 发现与来源管理界面

“安装 Skill”打开参考 cc-switch 的发现页面。在线发现区至少包含两个视图：

- **仓库**：展示本地已登记和随应用提供的推荐 GitHub 来源；用户可以通过来源管理添加 `owner/repo`、GitHub URL 和可选 branch；
- **skills.sh**：按关键词搜索外部服务，并把可验证结果转换成 Source。

GitHub 输入可以是仓库根 URL，也可以是包含 `/tree/<ref>/<path>` 等 branch 和子目录信息的 Skill URL。Adapter 解析出 `owner/repo`、ref 和成员路径后，必须把完整仓库登记为 Source。成员路径只是发现提示：获取完整 Source 目录后高亮匹配的 Skill；它不能改变 Source 边界、直接安装默认全选的规则，也不能让同一仓库被拆成多个子目录 Source。Bundle 只在用户确认安装后创建。

用户在发现页首次登记 GitHub Source 时，Adapter 优先使用并验证 URL 或用户输入中明确给出的 ref。输入没有 ref 时，Adapter 读取仓库 metadata 中的 default branch，并持久化解析出的实际 branch 名；不能猜测 `main`、`master` 或其他名称，也不能把动态的“default”标记保存为 Tracked Ref。显式 ref 或 default branch 无法访问时，本次登记失败，不创建 Source、Bundle、Member Selection 或受管内容。接管是唯一例外：lock 已经确认仓库但没有保存 ref 时，接管事务以 GitHub 的 `HEAD` ref 保存 Source，不为完成接管额外联网；它明确表示后续跟随仓库当前默认分支，不伪装成已知的具体 branch。

Source Adapter 必须先把输入解析为 canonical Source identity。推荐来源、`skills.sh`、直接 URL、成员 URL、扫描到的安装证据或 Installation Chain 只要指向同一个上游，都复用同一个 Source；新入口只追加来源证据和成员提示。一个 Source 在本机最多关联一个 Bundle。若该 Source 已关联本地 Bundle，安装页复用该 Bundle；若 Bundle 尚未创建或已经删除，则保持只有 Source，直到用户再次确认安装。GitHub 的 canonical Source 是完整仓库，同一仓库的不同 URL 形式、ref 和子目录提示不能创建第二个 Source 或第二个 Source-backed Bundle。

一个 GitHub Source 只能有一个 Tracked Ref。新发现入口携带不同 ref 时，界面展示当前值和候选值，不能覆盖当前设置或创建第二个 Source。用户明确确认切换后，Adapter 先验证候选 ref 可访问，再更新 Source 的 Tracked Ref；验证失败则保留原值。成功切换不会替换当前受管内容或修改 Mount，只改变后续成员发现、Update Check 和更新获取使用的 ref。

GitHub Adapter 在 1.0 中只访问公开仓库。SkillYard 不实现 GitHub 登录、OAuth、token 输入、credential helper 或私有仓库权限检测，也不在 SQLite 中保存 GitHub 凭据。私有仓库内容必须先由用户通过其他工具取得，再通过本地目录或 ZIP 进入 Source 登记、安装和成员选择流程。

发现页面中的在线结果统一按 Source 分组。仓库视图直接以已登记 Source 为单位展示；`skills.sh` 搜索结果必须先解析为可验证的 Source，同一 Source 的多个命中合并到一个组中，并高亮与关键词匹配的 Skill。无法解析到受支持 Source 的结果不能直接安装。

选择一个 Source 后，SkillYard 获取完整成员目录并展示可安装 Skill。直接安装默认选择全部成员，用户可以在最终确认前取消不需要的成员；未选择成员继续留在 Source 目录中，不进入本地 Bundle。ZIP、本地目录、通用 URL 和接管已有安装作为同一安装区域内的其他入口，不要求用户先理解 Adapter。

当发现入口命中已经登记的 Source 时，界面直接进入该 Source 的详情。Source 已关联 Bundle 时，同时显示已经安装的 Skill Member 及其 Mount 状态，并从安装选择中禁用；只有尚未安装的可用成员能够加入 Member Selection。Source 没有 Bundle 时，用户确认安装后创建本地 Bundle。全部成员均已安装时不建立空安装事务。安装动作不能覆盖已安装成员的当前受管内容或 Mount；需要采用新内容时必须进入普通更新或 Manual Replacement Update。另一个已接管 Bundle 后续关联到该 Source 时进入来源关联归并流程，不通过安装页建立第二个 Bundle。

Skill Member 发现只使用一个文件系统边界规则：每个文件名严格为 `SKILL.md` 的普通文件定义一个 Member，其父目录就是 Skill 根目录。Source 不需要 manifest 才能发现成员；如果完整来源中没有 `SKILL.md`，界面显示“未发现 Skill”，不能进入成员安装事务。Adapter、官方 index 或 manifest 可以补充 Source、成员路径提示和展示 metadata，但不能把缺少 `SKILL.md` 的目录登记为 Skill Member。

发现完成后必须比较所有 Skill 根目录。只要一个 Member 的 `SKILL.md` 位于另一个 Member 的根目录之下，这组父子 Member 都进入 Nested Skill Conflict，不能被选择用于安装、接管或更新。界面展示各自的 `SKILL.md` 路径和重叠关系，但不提供“只选其中一个”、自动排除子目录、复制内容或重新划分根目录的选项。用户需要先在来源或已有安装中把它们整理为互不嵌套的目录，再重新扫描。

Nested Skill Conflict 只阻止参与重叠的 Member 进入直接安装或接管；同一 Source 中其他根目录互不重叠的 Member 仍可进入这些成员级流程。Bundle 更新固定安装 Source 的全部当前成员，因此任一 Member 发生冲突时，整个 Bundle 更新在生效前失败，所有当前受管内容、Mount 和 Member Selection 保持不变。

### SKILL.md 最低格式

Codex、Claude Code 和 GitHub Copilot 的官方 Skill 文档都要求 `SKILL.md` 使用 YAML frontmatter，并至少包含 `name` 和 `description`。SkillYard 1.0 使用三者共同采用的 Agent Skills specification 作为统一最低验证，不建立三套 Host-specific 内容格式：

- `SKILL.md` 必须是可读取的普通文件，YAML frontmatter 必须能够解析；
- `name` 必填，长度为 1–64，只允许小写 ASCII 字母 `a-z`、数字 `0-9` 和连字符 `-`；
- `name` 不能以连字符开头或结尾，不能包含连续连字符，并且必须与 Skill 根目录名完全一致；
- `description` 必填且非空，长度为 1–1024；
- 其他可选字段和 SkillYard 不认识的字段原样保留，不作为拒绝理由；
- Markdown 正文不做内容质量、完整性或效果判断。

同一 Bundle 完成成员发现后，必须按 `name` 检查唯一性。两个或更多不同 Skill 根目录声明相同 `name` 时，所有重复成员都验证失败；错误只展示重复名称和各自的 `SKILL.md` 路径，不提供合并、自动改名、别名或覆盖选项。该校验是低频保护，不增加独立管理状态或专用修复工作流。

Bundle 更新固定安装全部成员，因此发现任一重复名称时整个更新在生效前失败；已有 Skill 继续使用原受管内容。

不同 Bundle 可以包含同名 Skill，因为主界面按 Bundle 分组，SkillYard Presentation Label 也包含 Bundle Display Name。它们仍是不同 Skill Identity；如果用户把它们挂载到同一个 Supported App 和 scope，目标目录同名会进入既有 Mount Conflict。

不符合规则的文件仍可以在扫描结果中显示为无效 Skill Candidate，并列出 YAML、缺失字段、长度、字符或目录名不一致等具体错误，但不能创建受管内容、Member Selection 或 Mount。接管不修改原目录；更新或手动替换在替换 Bundle `current` 前失败，继续保留原完整 Bundle。

格式依据：[Codex Build skills](https://learn.chatgpt.com/docs/build-skills)、[Claude Agent Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)、[GitHub Copilot Agent Skills](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/add-skills) 与 [Agent Skills specification](https://agentskills.io/specification)。

SkillYard 1.0 直接采用 cc-switch `3.17.0` 当前内置的四个 GitHub Source，首次使用时作为已添加来源存在：

| Source | Branch |
| --- | --- |
| `anthropics/skills` | `main` |
| `ComposioHQ/awesome-claude-skills` | `master` |
| `cexll/myclaude` | `master` |
| `JimLiu/baoyu-skills` | `main` |

该列表作为“仓库”视图的初始内容，随 SkillYard 应用版本发布，不从远程服务动态下发，也不缓存或托管对应 Skill 内容，因此不构成公共 registry。四个来源与用户后来添加的 Source 一样可以维护或删除；1.0 不保存启用／停用状态。用户添加的仓库、Bundle、成员目录和安装记录都保存在本地 SQLite。

首次扫描和应用启动都不访问这些初始来源。用户进入“安装／发现 Skill”页面时，SkillYard 才通过受支持的 GitHub Adapter 获取当前已添加来源的成员目录；页面中的后续重新获取必须由用户点击局部的“重新加载来源”。`skills.sh` Adapter 只在用户提交搜索关键词时发出请求，不执行预取、启动查询或后台轮询。这个局部动作不等同于主界面的“刷新本机”或“检查更新”。

一次网络 Source 重新加载只有在完整成员目录获取和验证成功后，才能原子替换 SQLite 中的上次成功目录并更新成功时间。请求失败、超时、响应无效或验证失败时，SkillYard 保留上次成功目录和时间，同时记录本次失败并在 Source 页面标记“刷新失败”。失败不能产生空目录、Upstream-removed Skill 或其他成员可用性变化。

保留的 Stale Source Catalog 只用于浏览和说明来源历史。安装新成员与 Bundle Update 必须保持不可用，直到 Adapter 再次成功获取该 Source 的当前内容；成功后使用新目录继续普通确认流程。已有 Bundle、当前受管内容、Member Selection 和 Mount 不受影响。若该 Source 从未成功加载，页面只展示错误和重试入口，不展示推测或空成员列表。SQLite 保存的只是成员路径、名称和获取状态等目录 metadata，不保存一份可离线安装的上游 Skill 内容。

这一界面参考已经过源码核验的 cc-switch `3.17.0` 安装流程，但实际写入必须遵守 SkillYard 模型：安装结果先进入临时区验证；直接安装默认选择全部成员；安装完成后保持“已安装、未挂载”；Supported App 仅为 Codex、Claude Code 和 GitHub Copilot；Mount 只使用软链接。cc-switch 的立即挂载、扁平 Skill 记录和 copy 回退不能照搬。实证见 [cc-switch 3.17.0 Skill 管理机制核验](research/cc-switch-skill-management.md#1-安装与发现入口)。

### 外部安装命令边界

SkillYard 1.0 不执行 `npx skills`、`gh skill`、Lark CLI 或其他外部命令来安装或更新 Skill。用户可以按发布者说明在 SkillYard 之外运行这些命令；首次扫描或后续“刷新本机”发现结果后，SkillYard 只自动解析已经核验的 lock v3，并把其中的 Source URL／路径、上游 Skill 路径、ref、内容 marker 和时间保存为 Installation Chain。

lock v3 是多种工具共用的收据协议，不能证明具体执行者。它能够规范化到 SkillYard 支持的 GitHub Source 时，用户确认接管会自动创建或复用该 Source 并关联 Bundle；无法规范化或缺少这类证据时仍保持 Unknown Provenance。Lark 专属状态、GitHub frontmatter 和其他 receipt／manifest 格式不属于 1.0 自动发现范围。

外部命令的存在性与真实能力仍记录在 [Skill Provider CLI 存在性与边界核验](research/skill-provider-cli-evidence.md)，但这些事实只用于来源恢复和接管解释，不构成 1.0 command Adapter 承诺。

全新安装的成员选择页默认勾选 Source 中全部已发现 Skill，用户可以在确认前取消任意成员。确认后，SkillYard 创建或补充本地 Bundle，只为最终选择保存受管内容、写入 Member Selection，并进入后续挂载流程；未选择成员只保留在 Source 目录中。挂载不是完成安装的前置条件，用户可以暂时不选择任何 Host。

只要用户提交安装时的最终 Member Selection 没有包含当前 Source 目录中的全部有效成员，确认区就显示一次部分安装风险提示：同一 Bundle 中的 Skill 可能互相引用，SkillYard 1.0 不检查依赖关系，继续后可能无法正常使用。该提示不自动修改选择、不增加第二层确认，也不阻止用户继续。1.0 不从 Markdown 链接、相对路径、脚本、import、manifest 或命名约定推导依赖图，不自动补选成员，也不承诺部分安装可以独立运行；这项风险由用户承担。显式 Bundle Update 仍会安装 Source 的全部有效成员。

### Skill 内代码边界

SkillYard 在发现、扫描、接管、安装、结构验证和更新过程中都不执行候选内容中的任何代码，包括 shell、Python、Node 脚本、二进制文件、安装脚本和 lifecycle hook。所有内容只在临时区被读取和验证，随后按普通文件保存为受管内容；验证器不能通过运行文件来判断它是否有效。

影响预览必须提示内容中检测到的脚本或可执行文件。1.0 使用文件类型、扩展名、可执行位和常见脚本目录进行确定性标记，并可以展示数量与路径；提示文案必须明确这不是完整的恶意代码扫描，也不代表 Skill 安全。Skill 挂载以后，Agent 应用是否根据 Skill 指令运行这些文件，不属于 SkillYard 的执行职责。

### 受管 Skill 只允许普通文件和目录

每个 Skill Member 在进入 Central Store 前必须递归检查目录项，且检查过程使用 `lstat` 等不跟随链接的方式。可进入 Current Content 的条目只有普通目录和普通文件；以下内容都会使 Member 验证失败：

- symbolic link，无论是相对路径、绝对路径、指向内部还是指向外部；
- hard link，包括本地目录中能够识别出的多链接文件和归档中声明的硬链接条目；
- FIFO、Unix socket、字符设备、块设备及其他特殊文件系统条目。

界面列出发现的路径和不受支持的条目类型，但不提供“仍然安装”、自动解引用、复制目标、转换类型或修复内容的选项。普通脚本、二进制文件和可执行文件仍属于普通文件，可以保存；它们继续遵守“不执行候选代码”和影响预览规则。

归档输入在写出文件前逐项验证路径。条目必须是相对路径，并且规范化、拼接后的目标仍位于本次临时区内部；绝对路径或任何逃出临时区的目标使整个归档输入立即失败。验证器不能先写出再检查，也不能在失败后保留部分解压结果。

- 直接安装：失败 Member 不能留在最终 Member Selection；其他有效 Member 仍可被用户选择，但确认后的事务不接受部分失败；
- 接管已有安装：只读扫描发现不受支持条目后，不能为该 Member 生成可执行接管计划，也不移动、替换或删除原目录；
- 更新或手动替换：任一候选 Member 失败时，整个 Bundle 在替换其唯一 `current` 前失败，全部当前受管内容、Mount 和 Member Selection 保持不变；
- Source 中其他有效 Member 不因一个 Member 失败而失去有效性，但完整 Bundle 更新不能排除失败 Member；用户需要先修复来源再重新更新。

这条规则只约束 Source 候选和 Skill 受管内容。SkillYard 在 Managed Bundle Directory 中创建的 `current`，以及在 Supported App 路径创建并指向稳定成员路径的 symbolic-link Mount，仍然是合法的管理结构。

### 网络获取与归档展开限制

GitHub、URL、ZIP、`.skill` 和其他由 Adapter 获取或展开的输入必须遵守以下固定 Source Resource Limit：

| 计数器 | 1.0 上限 |
| --- | ---: |
| 累计接收字节数 | 100 MiB（104,857,600 bytes） |
| 归档条目数 | 20,000 |
| 展开后的普通文件总字节数 | 512 MiB（536,870,912 bytes） |
| 单个普通文件字节数 | 100 MiB（104,857,600 bytes） |

Adapter 在读取响应流和写出每个普通文件前持续维护四个独立计数器；下一次读取或写出会使计数超过对应上限时，立即停止继续处理。不能依赖 HTTP `Content-Length`、归档头声明值或解压完成后的磁盘统计作为唯一检查。

超限属于整个 Source 输入失败，不是可从 Member Selection 排除的成员错误：

- 首次登记或重新加载 Source：不采用不完整目录；存在 Stale Source Catalog 时继续保留上次成功目录；
- 直接安装：不创建或补充 Bundle、Current Content、Member Selection 或 Mount；
- Bundle Update 或手动替换：不切换 `current`，已有受管内容与 Mount 保持不变；
- 所有路径都清理本次临时内容，并显示触发的限制名称、固定上限和已检测值。

1.0 不提供修改限制、按 Source 放宽限制或“仍然继续”的入口。限制用于阻止失控下载、超大归档和压缩炸弹，不代表对 Skill 内容安全性的完整判断。

### Editable Local Source

个人 Skill 的编辑位置与托管运行位置必须分开。用户明确指定的个人目录或本地 Git clone 可以登记为 Editable Local Source；它仍由用户拥有并编辑，但 Host 不直接使用其中的可变内容。明确由项目仓库维护的 Skill 不自动转换为 Editable Local Source，仍保持 Project-managed Installation。

本地修改进入 SkillYard 的流程是：

```text
用户编辑 Editable Local Source
  → SkillYard 对照上次采用内容检测变化
  → 展示本次完整 Bundle 的安装影响
  → 用户确认
  → 为全部当前 Skill 准备候选内容
  → 原子替换已有成员的 current，并安装新增或尚未安装的成员
  → 已有 Mount 通过 current 同时跟随；新增成员保持未挂载
```

在用户确认更新前，新发现的 Skill 只更新 Source 的可用成员目录；更新成功后，全部当前成员安装进 Bundle 并加入 Member Selection。Managed Bundle Directory 不是编辑工作区；对其中受管内容的外部修改不构成可发布的本地更新，也不能静默传播到 Mount。SkillYard 1.0 不提供这类外部修改的检测、差异查看、自动修复或转存流程，具体处理留给后续版本决定。

#### 来源不可用

Editable Local Source 的登记路径无法读取时，SkillYard 将 Source 标记为 Unavailable Source，并暂停从该来源发现成员或采用修改。这个状态不改变 Local Lifecycle Authority，也不修改当前受管内容、Member Selection 或 Mount；已经安装和挂载的 Skill 继续工作。

用户重新指定来源路径时，SkillYard 必须先扫描新位置，展示 Source 目录、关联 Bundle、Skill Member、来源证据与内容差异，再由用户确认关联。名称或目录结构相似不能静默改写 Source。重新关联只恢复后续更新能力，不立即替换当前受管内容。

### 两种安装路径

```text
接管已有安装
  → 读取现有 Host 使用位置
  → 把选中内容与已有成员准备为 Managed Bundle Directory 中的完整候选 Bundle
  → 验证候选 Bundle 并建立或替换唯一 current
  → 在原 Host 路径重建指向稳定成员路径的软链接 Mount
  → 验证原 Host 仍可发现 Skill

SkillYard 直接安装
  → 获取 Source 当前内容到临时区
  → 默认选择全部 Skill Member，用户确认最终选择
  → 写入并验证完整候选 Bundle
  → 原子建立 Bundle 唯一的 current
  → 用户选择零个或多个 Supported App 与 scope；project scope 只能选择已登记项目
  → 有选择时创建指向各稳定成员路径的软链接 Mount，并验证所选应用可发现 Skill
  → 无选择时保存为“已安装、未挂载”
```

macOS 1.0 的 Central Store 根目录固定为 `~/Library/Application Support/SkillYard/`。每个 Bundle 的 Managed Bundle Directory、完整当前受管内容和唯一 `current` 是用户已接管 Skill 的实际主副本，不是缓存或普通应用数据；SQLite、临时区、事务恢复临时内容和 Filesystem Transaction Journal 使用该根目录下由 SkillYard 控制的独立子路径，从而默认处在同一本地文件系统。界面提供“在 Finder 中打开”，但不提供位置设置、目录迁移或外置磁盘模式。

根目录持续保存由 SkillYard 生成的 `SKILLYARD-INFO.md`。它以人类可读方式说明 Central Store 包含用户 Skill 的实际主副本、不能作为缓存删除，并列出已知 Source 与每个 Host／project Mount 位置。成功完成安装、接管、挂载、Source 或 Bundle 删除、来源变更后，SkillYard 同步更新该文件；它用于说明和人工调查，不取代 SQLite 或 Filesystem Transaction Journal。

Central Store 不能被 Agent 应用直接扫描。`~/.agents/skills` 和项目 `.agents/skills` 等会被多个应用共同扫描的目录不能充当主副本目录，也不能接收 SkillYard 新建的 Mount；它们只用于只读 Inventory、Management Evidence 和已有安装 Takeover。新 Mount 只写入固定应用专属路径，并指向 Managed Bundle Directory 中 `current` 下稳定成员路径。

SkillYard 只替换用户明确接管的单个 Skill 根目录，不替换任何 Supported App 的整个 Skill 根目录。目标目录中的 Host 内置内容、插件管理内容、项目仓库维护内容和其他未接管 Skill 必须保持原状；根目录级软链接不属于合法 Takeover Plan 或 Mount。

### Project 列表

SkillYard 维护一份保存在 SQLite 中的本地 Project 列表。项目只能通过以下两种方式加入：

- 用户主动选择一个项目根目录；
- 接管已有 project Skill 时，SkillYard 识别出所属项目并由用户确认。

发现项目线索不能直接创建 Project 记录。SkillYard 1.0 不扫描整块磁盘来枚举 Git 仓库或推断项目，也不把任意包含 Skill 目录的路径自动登记为项目。每个 Project 记录只需保存项目根目录；只有已登记项目才能创建新的 project Mount。

1.0 假设 Project 都位于当前 Mac 的本地、持续可访问目录中。它不建立 Project 不可用、Mount 无法检查、外置磁盘重连或项目根目录恢复流程；真实使用中出现这类需求后再扩展模型。

Project 记录创建后，SkillYard 立即根据 Codex、Claude Code 和 GitHub Copilot 的内建应用路径配置，只读扫描该项目中实际存在的 project Skill 目录。扫描结果展示每个现有 Skill 的位置和管理方，并区分 SkillYard-managed、待接管、Agent 应用管理与项目仓库管理；不存在的目录直接跳过。

这次项目盘点不创建 Managed Bundle Directory、受管内容、Member Selection 或 Mount，也不移动、替换或删除项目中的文件。用户选择管理某个待接管 Skill 时，必须另行生成接管计划并确认，不能把“添加项目”同时解释为接管授权。

从 Project 列表移除一个仍有 SkillYard-managed project Mount 的项目时，影响预览必须列出该项目中的全部 managed Mount、对应 Skill 和 Supported App。用户确认后，SkillYard 按一个事务移除这些 Mount；只有全部目标均完成并通过验证后，才删除 Project 记录。任一步失败都保留 Project 记录，并恢复本次已经移除的 Mount，避免出现数据库已忘记项目但文件系统仍有部分挂载的状态。

移除 Project 不删除其中使用的 Skill。Managed Bundle Directory、Member Selection、当前受管内容，以及其他项目或应用中的 Mount 均保持不变；因此失去最后一个 Mount 的 Skill 只会回到“已安装、未挂载”。扫描发现的 Agent 应用管理或项目仓库管理内容不属于本事务，不能被修改或删除。

### 挂载 scope

对同一个 Skill 与 Supported App 组合，合法状态只有以下三种：

- 没有 Mount；
- 一个 global Mount；
- 一个或多个 project Mount，但每个 project root 最多一个。

global Mount 与任何 project Mount 不能同时存在。普通挂载请求创建 global Mount 时如果已有 project Mount，或者创建 project Mount 时已有 global Mount，都形成 Scope Conflict 并阻止写入。用户必须先通过独立操作移除已有 Mount，再创建另一种 scope；SkillYard 1.0 不自动转换或合并这两个动作。唯一例外是接管前已经同时存在两种 scope 的非托管安装，此时按已确认的接管计划在一个事务中收敛为用户选择的 scope。相同 Skill 在不同 Supported App 中的 scope 独立计算。

### 挂载冲突

创建或校正 Mount 前，SkillYard 必须检查目标 Host 路径：

- 路径不存在：可以按已确认的挂载计划创建软链接。
- 路径已经是该 Skill 的正确软链接：不视为冲突，只验证文件系统与 SQLite 记录一致。
- 稳定证据证明现有内容是同一 Skill，但它尚未被正确接管或链接：生成接管或链接校正计划，用户确认后再修改。
- 路径属于其他 Skill，或 Skill Identity 无法确认：标记为 Mount Conflict，阻止写入并保持现有内容不变。

Skill Name、目录名、描述或内容相似本身不能证明是同一 Skill。SkillYard 1.0 不通过自动覆盖、自动改名或一键替换绕过 Mount Conflict。占用者即使是另一个 SkillYard-managed Mount，也必须先通过独立操作移除，再重新发起当前挂载；SkillYard 不把这两个动作合并成替换事务。Host-managed Installation 和 Project-managed Installation 仍遵守只读边界，不能作为冲突解决过程被替换。

Bundle 分组中的批量挂载只是多个 Skill Mount 的统一入口，不会创建 Bundle 级软链接。预览阶段必须检查全部选中成员及其目标路径，并把每个 Mount Conflict 精确关联到对应 Skill、Supported App、scope 和占用路径。用户可以取消冲突成员，或退出后处理占用路径并重新发起；仍有冲突的计划不能确认。

确认后的最终 Mount 集合进入一个 Filesystem Transaction Journal。SkillYard 逐项创建并验证软链接，但在全部目标验证成功前不能提交成功状态。任一项在执行阶段失败时，事务删除本次已经创建的 Mount、恢复本次修改的 SQLite 关系，并保留执行前已经存在且正确的 Mount，使整个批量操作回到开始前状态。界面不能把已完成的部分显示为批量成功，也不能让用户在操作开始后接受部分结果。

### Mount Drift 与修复

SQLite 中存在 Mount 记录，但对应路径已经被删除、不是预期的软链接，或软链接指向了其他内容时，该 Mount 进入 Mount Drift。SkillYard 保留原记录、预期目标和使用关系，只更新健康状态；检测本身不能静默重建软链接、删除占用内容或把记录当作已正式移除。

用户主动执行修复时，SkillYard 再检查目标路径并展示计划：

- 目标路径为空：用户确认后创建指向该 Skill 在 Bundle `current` 下稳定成员路径的正确软链接，并在验证成功后恢复健康状态；
- 目标路径是普通文件、目录或指向其他内容的软链接：进入 Mount Conflict，修复停止，不覆盖或删除占用者。

用户也可以选择正式移除异常 Mount。这个操作只删除 SkillYard 的 Mount 使用关系；如果路径中存在无法验证为该 Mount 的内容，SkillYard 不删除它。移除最后一个 Mount 后，Skill 保持“已安装、未挂载”，其 Managed Bundle Directory、当前受管内容和管理能力继续保留。

### Mount Drift 检查时机

SkillYard 在启动恢复未完成事务后，对全部已登记 Mount 执行一次本地只读健康检查，并在用户主动执行“刷新本机”时重新检查。检查只比较 SQLite 中记录的 Mount 路径、预期 Bundle `current` 目标和稳定成员路径与当前文件系统状态，不能创建、改写或删除文件，也不能自动执行修复。

1.0 不使用文件系统监听，不在后台持续轮询 Mount，也不因检查结果改变当前受管内容或管理权。Mount 健康检查与上游更新检查是两套独立行为：前者可以在启动时读取本地状态，后者仍然只在用户主动点击检查更新后访问上游。

macOS 1.0 的 SkillYard-managed Mount 只使用软链接。SkillYard 不把实体内容直接写进 Host 目录，也不在软链接失败时静默改用复制；否则中央更新无法可靠传播到所有使用位置。

这一拓扑沿用 cc-switch 已验证的“本地主副本 + 多 Host 投影”工作流，但保留 SkillYard 自己的 Bundle、项目级 Mount、事务恢复和 Host 只读边界。参考实证见 [cc-switch 的 Skill 管理机制与 SkillYard 可复用设计](research/cc-switch-skill-management.md)。

### 手动检查更新

SkillYard 1.0 不在应用启动时、后台或定时检查上游。主界面只提供一个全局“检查更新”按钮；用户点击后，经过验证的 Adapter 一次检查全部已关联本地 Bundle 且具备可检查上游的 Source，并把结果记录到对应关系上：

```text
用户点击“检查更新”
  → Adapter 只读查询上游
  → 记录检查时间、结果和可用上游更新标识
  → 显示“可更新”“已是最新”或“无法检查”
```

对 GitHub Source，1.0 只比较 commit SHA。新 Bundle 首次直接安装时保存该 Source 的 Tracked Ref 实际解析出的已采用 commit；向已有 Bundle 补装成员不推进这条基线，只有完整 Bundle Update 成功后才推进。检查时再次解析同一个 ref。SHA 不同就把关联 Bundle 标记为“可更新”，SHA 相同就是“已是最新”。检查阶段不下载仓库 archive、不计算 Skill 目录内容哈希，也不尝试确定哪个已安装成员发生变化。新 commit 即使只修改 README、元数据或未安装成员，也仍然构成这个 Bundle 的可用更新。

Tracked Ref 切换成功后，SkillYard 解析新 ref 当前 commit，并与上次采用的 commit 比较。不同则显示“可更新”，相同则显示“已是最新”；这一步不下载 Source 内容、不替换受管内容，也不更新已安装 Skill。用户之后仍通过独立的普通更新动作决定是否采用新 ref 上的内容。

结果显示在 Bundle 分组标题上。该 Bundle 中已经安装的 Skill 可以显示“随 Bundle 可更新”，但没有成员级网络检查；上游新增成员显示为“更新后将安装”。使用 ZIP 或直接文件 Source 的 Bundle 显示“手动更新”。没有关联 Source 的 Bundle 不进入查询队列，显示“没有更新来源”，但继续显示“由 SkillYard 管理”，不能被当作“已是最新”或“手动更新”。

与已登记 ZIP 或直接文件 Source 关联的 Bundle 不具备可检查的 Git 标识，因此不进入“可更新／已是最新／无法检查”三态，而是固定显示“手动更新”。用户必须从该 Bundle 发起“导入新内容”并选择替换文件；SkillYard 不在启动、检查更新或后台流程中重新访问原 URL，也不使用 HTTP metadata 或内容哈希推断远端变化。没有关联 Source 的 Bundle 不显示“导入新内容”。

替换文件先进入临时区，SkillYard 重新发现 Bundle 成员并按既有 Skill Identity 规则展示影响范围。用户确认后，SkillYard 安装替换文件中的全部有效 Skill，不提供成员级排除；新增和此前未安装的成员都会安装并保持未挂载。该流程满足 Managed Lifecycle 中的更新能力，不把这类安装降级成非托管状态。

`skills.sh` 只负责发现。一旦结果解析到 GitHub Source，关联 Bundle 的更新检查与执行都采用 GitHub commit 规则。Editable Local Source 仍通过确认后采用本地内容进行更新，不使用 Manual Replacement Update。

这次检查不能获取候选内容到本地、替换当前受管内容或修改 Mount。检测到新上游标识后，界面提供独立的“更新”动作；只有用户主动执行更新，才进入下面的更新事务。检查与更新不能由一次点击静默串联。

“检查更新”不扫描本地 Skill 目录；“刷新本机”也不调用 Upstream Adapter。两个动作可以更新同一条 Skill 的不同状态，但不能相互隐式触发。

### 执行更新

更新遵循同一条路径：

```text
Adapter 获取上游内容到临时区
  → 识别 Source 的完整当前成员目录
  → 与必须保留的现有成员共同准备完整候选 Bundle
  → 验证将写入 Bundle 的完整候选内容树
  → 原子替换 Bundle 唯一的 current
  → 已有 Mount 通过 current 同时跟随；新增成员保持未挂载
  → Member Selection 更新为全部当前成员
```

每个可更新 Bundle 都提供单独的“更新”入口。存在多个可更新 Bundle 时，主界面同时显示“全部更新”。用户点击“全部更新”后，各 Bundle 的候选内容分别进入自己的临时区；SkillYard 再汇总展示参与的 Bundle、将安装的全部成员、现有 Mount 和新增安装。用户可以增减参与的 Bundle，不能排除某个参与 Bundle 中的单个 Skill；确认前不替换受管内容或修改 Mount。

“全部更新”是批量协调，不是一个跨 Bundle 的原子事务。确认后，每个 Bundle 按确认顺序逐个验证并执行既有更新事务，不并发修改托管状态；单个 Bundle 失败时保留该 Bundle 的原状态，但不阻止后续 Bundle 继续。完成页统一列出成功、失败和未执行结果。每个成功更新的 Bundle 都安装其完整有效成员目录，包括此前未安装和上游新增的成员。

更新确认只表达管理影响，不解释内容变化。每个 Bundle 显示本次将安装的全部 Skill、其中哪些是新增安装，以及现有 Supported App 和 Project Mount；不提供成员选择。GitHub Source 提供“查看上游”链接。1.0 不生成或展示文件 diff、逐文件变化列表、文件数量统计、自动 changelog 或 Skill 行为变化摘要。手动替换来源没有稳定发布页时不伪造变更说明。候选内容仍必须经过完整结构和安全边界验证；发现脚本或可执行文件时显示一个简短风险提示，但不展开为代码审查界面。

GitHub Source 关联的 Bundle 在执行阶段不使用“成员内容必须改变”作为过滤条件。当前 commit 中的全部 Skill 都参与更新；此前未安装或新增的成员都会安装。

进入生效阶段前，SkillYard 必须完整准备并验证本次 Bundle 更新的候选内容树。它包含 Source 的全部当前有效成员，以及需要保留的上游已移除或“不对应”成员。任一成员在成员发现、目录边界、frontmatter、名称唯一性、Safe Skill Content 或其他既有规则上失败时，整个 Bundle 更新失败，清理完整候选，不切换 `current`，也不新增成员。只有全部候选通过后才能开始生效。

每个 Bundle 只有一份完整当前受管内容和一个有效的 `current`，状态不属于某个 Host 或 Mount。同一 Skill 的全部 Mount 都指向该 Bundle `current` 下同一个稳定成员路径。SkillYard 1.0 不支持按 Host 使用不同内容，也不提供版本历史、旧内容选择或回滚入口。外部工具不能绕过这条路径直接覆盖当前受管内容。上游作者仍负责发布新内容；更新由用户发起或确认，不静默自动执行。

更新中新安装的 Skill 进入新的完整 Bundle `current`，但更新事务不为它创建或恢复 Mount；因此它保持“已安装、未挂载”，不会自动出现在任何 Supported App 中。

上游新增的 Skill 在检查或发现阶段只更新 Source 的可用成员目录；用户真正更新 Bundle 后，它与此前未安装的成员一起进入 Member Selection，但都不自动创建 Mount。用户在外部运行 Lark CLI 等工具后，新写入的内容可以再次被扫描，但外部工具不能决定已接管 Bundle 的 Member Selection 或修改受管主副本。

如果最新成功获取的 Source 内容已不再包含某个已安装 Skill，SkillYard 保留它的当前受管内容、Member Selection 和 Mount，并标记为“上游已移除”。它不参与这次内容更新，也不会被自动删除。用户可以移除它的 Mount；受管内容只在整个 Bundle 被删除时移除。这个状态不改变 SkillYard 的本地管理权。

### 原子生效与启动恢复

每个 Managed Bundle Directory 保存一个由 SkillYard 创建的 `current` 软链接，它指向包含全部已安装成员的完整内容树。Host 与 project Mount 永远指向 `current` 下各自的稳定成员路径，不会直接指向某次候选内容。安装和更新只有在完整候选 Bundle 写入临时区并通过验证后，才原子替换这一个 `current`。这次替换就是整个 Bundle 唯一的内容生效点；所有成员同时切换，已有 Mount 本身不需要重写。

任何可能修改文件系统的生命周期操作，都必须在首次变更前写入两类恢复证据：

- SQLite 事务记录：保存操作身份、相关 Skill、总体状态以及当前持久化阶段；
- Filesystem Transaction Journal：在替换 Bundle `current` 前持久记录旧目标与预期新目标，并保存具体路径、临时区、临时恢复内容、持久化阶段和已完成步骤。

最终确认是用户退出写操作的最后边界。确认前，用户可以修改选择或放弃计划；确认后，SkillYard 建立生命周期事务，界面不再提供取消或强制停止。关闭进度界面不能改变事务状态，事务只能完成或进入明确的阻塞恢复状态。进程退出、系统终止或崩溃按中断处理，并由同一 Journal 机制在下次启动时恢复，不能被解释为取消成功。

SQLite 和文件系统共用一个应用级写入门。任意时刻最多存在一个正在运行、会改变托管状态的生命周期事务；事务结束或进入明确的阻塞恢复状态前，其他安装、接管、挂载、更新、Project 移除或 Cascading Delete 入口不能建立新事务。1.0 不提供多个写事务并发执行，也不保存由用户任意堆积的后台写任务队列。

“全部更新”是唯一的内建批量协调流程：它保存本次已经确认的 Bundle 顺序，每次只启动一个 Bundle 事务，当前 Bundle 达到成功或失败终态后才启动下一个。这样仍然保持各 Bundle 独立恢复和独立结果，不把批量操作升级成跨 Bundle 原子事务。

单写事务不会把应用切换为不可操作的全屏锁定状态。列表、搜索、筛选和已提交详情保持只读可用；顶部当前操作提示在所有这些页面中持续存在。受影响对象以事务叠加状态显示“处理中”，只有达到成功、失败或阻塞恢复终态后才展示最终管理状态。

SQLite 数据库事务只能保证数据库内部提交，不能让文件移动、软链接替换和目录删除一起具备原子性。接管、Cascading Delete、移除 Project 等多路径操作必须把每一步设计为可重复执行，并在完成后持久化下一阶段；进程再次执行同一步时不能制造第二份受管内容、Mount 或删除额外内容。

应用启动时先处理 SQLite 中仍为未完成状态的事务，并同时核对 Journal 与实际 Bundle `current`，再执行普通 Mount 健康检查。实际目标等于 Journal 的旧目标时视为生效前，等于预期新目标时视为生效后，指向其他内容时不能猜测：

- 生效点之前中断：保留原有受管内容与 Mount，清理候选内容、临时区和本次新增但尚未确认的路径；
- 生效点之后中断：保留新的完整 Bundle，通过 Journal 继续完成 Mount、SQLite 记录、验证和清理；
- 多路径操作：从最后一个持久化阶段重放尚未完成的幂等步骤，直到事务达到成功或明确阻塞状态。

普通中断不会让用户选择内容状态。自动恢复成功后，界面只提示“已恢复上次中断的操作”。只有托管内容缺失、目标路径已被外部改写、权限异常或其他无法安全判定预期状态的情况，才阻塞相关 Skill 的写操作并显示人工恢复页面；其他 Skill 和只读功能继续可用。

### 1.0 不推断成员重命名

SkillYard 1.0 不建立成员重命名或路径迁移关系。上游名称、目录、描述或内容发生变化时，即使两份内容看起来相似，也不能自动或通过用户确认把它们合并成同一个 Skill Identity。

更新后，旧成员按“上游已移除”继续保留现有受管内容、Member Selection 和 Mount；新成员作为完整 Bundle Update 的新 Skill 独立安装并保持未挂载。Host Presentation Label 的前缀或格式变化仍然只是 Host 的展示行为，不改变任何 Skill Identity。

## 移除 Mount、删除 Bundle 与删除 Source

移除 Mount 只删除对应 Host 路径中的软链接和 Mount 关系。用户可以移除单个 Mount，也可以一次解除某个 Bundle 的全部 global 和 project Mount；全量解除只扩展现有 Removal Plan 的影响范围，不建立另一套事务或删除协议。移除最后一个 Mount 后，Skill 进入“已安装、未挂载”，继续保留 Source、Managed Bundle Directory、Member Selection 和当前受管内容。SkillYard 不得因为 Mount 数量变为零而删除 Skill。

SkillYard 1.0 不提供“卸载 Skill”“删除 Skill”、批量选择部分 Skill 删除，或保留 Bundle 但清空其已安装成员的入口。用户要停止使用某个 Skill 时移除其 Mount；要删除本地受管内容时删除整个 Bundle。Member Selection 在初次安装确认、Takeover、后续安装和 Bundle Update 中可以增加，但不能通过成员级删除操作缩减。

### 删除 Bundle

Bundle 是本地已安装组。删除 Bundle 会进入 Cascading Delete：

- 解除其中全部 Skill 的 global 和 project Mount；
- 删除 Member Selection、Managed Bundle Directory 和完整当前受管内容；
- 最后删除 Bundle 与其本地成员记录；
- 保留关联 Source、上游成员目录和来源管理记录，用户之后可以从该 Source 重新安装。

### 删除 Source

Source 是独立的上游来源记录。删除 Source 会删除其成员目录、检查结果、更新标识和与本地 Bundle 的更新关联，但不会删除 Bundle、Skill、Mount、Member Selection、Managed Bundle Directory 或当前受管内容。关联 Bundle 继续由 SkillYard 管理，并显示“没有更新来源”，所有更新入口不可用；用户重新添加并关联相同 Source 后可以恢复更新能力。删除 Source 不是 Cascading Delete。

1.0 不提供在一个操作中把 Bundle 从已关联 Source 改绑到另一个 canonical Source。用户必须先删除旧 Source，保留 Bundle、Skill 和全部 Mount，使 Bundle 暂时变成“没有更新来源”；随后再添加并通过普通来源关联流程关联新 Source。若新 Source 已有关联 Bundle，则按来源关联归并规则处理。这个流程不会隐式更新当前受管内容。Tracked Ref 切换和 Unavailable Editable Local Source 的路径修复只维护同一个 Source，不属于改绑。

四个初始推荐来源不具有特殊状态或删除保护。用户删除后，它们与普通 Source 一样从本地来源列表消失；需要再次使用时按普通添加流程重新添加。1.0 不提供启用／停用状态。

删除 Bundle 必须执行两层确认。第一层是完整影响预览，列出受影响的 Skill、Supported App、Project、Mount 和将永久删除的受管内容；第二层是独立的危险操作确认，明确说明确认后会级联删除全部列出成员。只有两次确认均完成后才能开始事务。删除 Source 只做普通确认，并列出将失去更新来源的 Bundle，不使用删除本地内容的危险文案。

Cascading Delete 的持久化阶段必须区分破坏性生效点。生效点之前失败或中断时恢复开始前状态；生效点之后则保留删除意图，并通过 Filesystem Transaction Journal 重试未完成步骤，直到全部成员和 Bundle 一起删除。外部修改或权限异常使自动完成不再安全时，事务进入人工恢复，而不能把部分结果显示为成功。事务成功后没有回滚入口。保留的 Source、上游 GitHub 仓库、用户拥有的 Editable Local Source 目录、Agent 应用管理内容和项目仓库管理内容不属于删除目标，不能被修改。

### 不保留本地版本

SkillYard 1.0 不创建本地版本号、版本历史或回滚点，也不提供旧内容选择、版本删除或 Revision 清理入口。更新事务成功后，旧内容不再作为可选状态保留；事务需要的临时恢复内容在完成后清理。Filesystem Transaction Journal 只保证当前操作可以安全完成或恢复，不构成面向用户的回滚功能。

## SQLite 记录范围

SkillYard 使用本地 SQLite 保存管理状态，至少包括：

- 首次扫描是否完成，以及最近一次“刷新本机”的时间、结果和本地只读 Inventory；
- canonical Source identity、可用性状态与来源履历，包括指向该 Source 的发现入口、Editable Local Source 路径、上次成功成员目录及其获取时间、最近重新加载结果和上次采用的内容指纹；
- 确定性的 Management Evidence，以及证据不足时的 Unknown Provenance 状态；
- 用户确认的 Source 关联，以及每个本地 Skill “对应”的 Member ID 或“不对应”结果；
- Source 的上次手动检查时间、检查结果和可用上游更新标识；GitHub Source 还记录所跟踪 ref、上次采用的 commit SHA 和最近检查解析出的 commit SHA；
- ZIP 和直接文件 URL Source 的原始来源信息、最近采用的 artifact digest、导入时间和事务记录；
- Bundle、其中本地已安装的 Skill Member，以及与 Source 的可选且唯一一对一更新关联；
- Skill Identity、上游名称与路径、用户确认的同名副本身份、来源关联及其证据；
- 用户持久化的 Member Selection；
- Skill Member 的上游可用性；
- 每个 Bundle 的当前受管内容引用、预期的 `current` 目标、已采用的上游更新标识，以及每个已安装 Skill Member 的稳定受管路径；
- Project 列表及其项目根目录；
- 项目使用关系；
- Managed Bundle Directory；
- 每个已安装 Skill 的零个或多个软链接 Mount，以及各 Mount 的 Supported App、scope、目标路径、预期链接目标和健康状态；
- 接管、安装、采用本地修改、更新、Cascading Delete、移除 Project 和恢复事务记录，包括当前持久化阶段与关联 Filesystem Transaction Journal。

Skill 内容、Bundle `current`、事务恢复临时内容和 Filesystem Transaction Journal 仍保存在本地文件系统中。SQLite 用于表达关系、状态和可恢复操作，并引用 Journal 完成启动恢复；SQLite 事务不能代替文件系统阶段记录。事务状态和 Journal 是内部正确性机制，不构成操作历史、活动页或日志产品。两者都不用于建设云端市场。

## 隐私与遥测边界

SkillYard 1.0 不收集或上传任何遥测。使用分析、设备或用户标识、自动崩溃与错误报告，以及 Skill 名称、Source URL、Project 或 Host 路径、文件名、Inventory 和 SQLite 状态等本机管理信息都不能离开当前 Mac。macOS 自己保存的崩溃报告不由 SkillYard 主动读取或上传。

只有用户明确触发 Source 获取、目录或搜索加载、Update Check 或 Bundle Update 时，SkillYard 才能发起完成该操作所必需的网络请求。请求只携带对应协议必需的数据，不能追加分析事件、遥测标识或设备画像。SQLite 事务记录和 Filesystem Transaction Journal 始终是本机正确性状态，不是遥测。

因为产品没有遥测，1.0 不建立遥测同意、退出、崩溃上传或隐私设置页。未来若要引入任何数据上传，必须作为新的产品决策重新定义边界，不能被视为普通实现细节。

## 应用本体与托管数据

`SkillYard.app` 与固定 Central Store 是两个独立的本地生命周期。用户把应用拖进废纸篓、替换应用版本或暂时移除应用本体时，不能触发解除 Mount、删除受管内容或清理 SQLite。Host 与 project Mount 仍然指向各 Bundle `current` 下对应的稳定成员路径，所以已经挂载的 Skill 继续工作；不转换为普通文件，也不要求用户预先运行准备流程。

重新构建并手动替换 SkillYard 后，应用先检测 `~/Library/Application Support/SkillYard/` 中的现有 SQLite、Journal、受管内容和 `current`，按普通启动恢复规则处理未完成事务，再恢复原有管理界面与生命周期能力。

“重置应用”是非破坏性操作，只能清除偏好设置、窗口状态和缓存。SQLite、Central Store、受管内容、`current`、Mount、Member Selection 和生命周期事务记录必须保留，重置后继续使用同一托管状态。

SkillYard 1.0 不提供“彻底清除 SkillYard”或全量移除所有托管内容与 Mount 的入口。完整移除流程留给后续版本；删除应用、重置应用和手动删除 Central Store 都不能冒充这项能力。

## 备份与恢复边界

SkillYard 1.0 不提供 Central Store 的备份文件、手动导出、从备份恢复、自动或定时备份、云备份以及跨设备迁移。用户或系统在 SkillYard 外复制目录不构成经过验证的 SkillYard 备份，1.0 不承诺能够从这类副本恢复 SQLite、受管内容、`current` 和 Mount 关系。

这里的“备份与恢复”不包括生命周期事务内部的临时恢复内容、Filesystem Transaction Journal 和启动中断恢复。后三者继续用于保证本机单次操作安全，但不能作为完整 Central Store 备份功能对外展示。备份与恢复是重要的后续版本主题，不改变 Central Store 作为持久用户主副本的性质。

## 不强行接管的边界

- Codex 插件或其他 Host 随应用提供的 Skill：展示来源和所在 Host，生命周期操作跳转到 Host。
- Host 内置 Skill：只读展示，不复制成 SkillYard 主副本。
- 明确提交在项目仓库中并由该仓库维护的 Skill：只读展示，操作跳转到项目。

如果用户日后把项目维护的内容明确移出仓库并要求 SkillYard 接管，那是一次新的、需要确认的接管事务，不能由扫描结果自动推断。

## AI 与来源判断边界

SkillYard 1.0 不捆绑或下载本地 LLM，也不调用云端模型。Source 恢复、Installation Chain、Bundle、Skill Identity、上游更新标识和接管判断只能来自确定性的 Management Evidence、经过核验的 Adapter 规则和用户明确确认。

证据无法确认来源时，Skill 保持 Unknown Provenance，并在界面显示“来源未知”。SkillYard 保留已经确认的文件位置、内容、Host 使用关系和安装线索，但不会生成候选 Source、置信度或 AI 推断结果。未来的解释或调查助手不得被视为 1.0 运行依赖。

Unknown Provenance 不构成接管阻塞条件。只要扫描和用户确认能够确定本地内容边界，接管事务就把当前内容保存为受管主副本，保留现有 Host 使用关系并按普通规则建立 Mount。接管后，管理状态显示“由 SkillYard 管理”，来源状态仍显示“来源未知”；这两个状态不能合并成一个标签。

Unknown Provenance 也不能成为猜测 Bundle 边界的理由。多个不同 Skill 没有共同安装组证据时分别建立 Bundle；同一个 Host 根目录只是扫描位置，不代表同一来源或同一删除范围。

来源未知的托管 Bundle 仍由 SkillYard 管理，因为其当前受管内容、Mount 和 Bundle 删除都在本地管理体系中。它同时显示“来源未知”和“没有更新来源”，不能执行更新；用户补充并关联 Source 后再恢复更新能力。

用户找到真实 Source 后可以发起来源关联。GitHub 仓库始终登记为完整 Source；对每个本地 Skill，界面只提供“对应”和“不对应”。选择“对应”后指定一个当前 Source 成员；选择“不对应”则不建立 Member 映射，也不记录或推断不对应的原因。一个 Source 最多关联一个本地 Bundle；如果它已经有关联 Bundle，本次关联必须先展示归并计划，不能增加第二条 Source-to-Bundle 关系。

归并计划以已经关联 Source 的 Bundle 为保留目标，列出待归入 Bundle 的全部 Skill、Mount、重复身份、内容选择和路径冲突。已有重复副本与 Mount Conflict 继续使用既有规则；任何必要选择未完成、冲突未解决或用户未确认时，不能开始事务。归并不是内容更新，也不会自动采用 Source 当前内容。

事务把待归入成员和 Mount 关系加入目标 Bundle 的完整候选内容，通过目标 Bundle 唯一的 `current` 生效，再校正并验证全部受影响 Mount 和 SQLite 关系。只有成功后才清理已经为空的原 Managed Bundle Directory 和 Bundle 记录。因为所有 Skill 内容和 Mount 都已转移，这不是 Cascading Delete，不使用两次危险确认。中断恢复仍遵守单一写事务和 Filesystem Transaction Journal：生效前保留两个原 Bundle，生效后继续完成归并与旧空记录清理。

来源关联不替换当前受管内容、不改变 Mount，也不静默执行首次上游更新。关联成功后，整个 Bundle 获得 Source-backed 更新路径；“对应”只建立本地 Skill 与当前 Source Member 的身份连续性，“不对应”不建立成员映射。Source 中其他当前成员在关联时只进入可用目录，不自动加入 Member Selection；用户之后主动更新该 Bundle 时，完整 Bundle 更新规则仍然生效：安装 Source 的全部当前有效成员，同时把“不对应”和上游已移除的既有成员保留在新的完整 Bundle 中。

对于选择“对应”的 Skill，SkillYard 不下载历史内容逐个匹配，也不使用内容哈希或相似度为当前受管内容猜测 commit。SkillYard 解析所跟踪 ref 的当前 commit，并立即把 Bundle 标记为“可更新”。当前内容保持不变，直到用户主动执行第一次上游更新。

第一次更新沿用普通更新事务：Source 的完整当前内容进入临时区，用户确认影响后安装全部当前有效成员。事务成功后，原有内容被替换且不作为旧版保留，Bundle 记录该 commit 作为已采用的上游基线；后续检查比较同一 Tracked Ref 当前解析出的 commit SHA 与这条已采用基线，二者不同时即显示可更新。

## 1.0 不承担的事情

SkillYard 1.0 不需要自建公共 Skill registry，也不需要维护市面上全部 Skill 的远程数据库。这不限制安装能力：安装入口可以直接携带来源，Adapter 也可以接入 GitHub、`skills.sh` 和确定可解析的 URL。

SkillYard 1.0 不是 shell 执行器，也不提供官方安装命令 Adapter。外部命令由用户在应用之外运行，SkillYard 只扫描和接管其结果。

SkillYard 1.0 也不是 AI Agent 或模型运行器，不使用模型参与管理决策。
