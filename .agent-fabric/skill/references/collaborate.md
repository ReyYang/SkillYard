# 日常协作

把协作当成一条证据链：明确任务、选择 Role、真实委派、复核声明、修正后再验收。多 Agent 只有在能降低风险、补充能力或并行独立工作时才值得使用。

## 1. 明确任务与所有权

当前 Agent 作为 `orchestrator`，先确定：

- 用户真正要得到的可观察结果，以及它为什么重要；
- 必要背景、已确定的接口和不能改变的决定；
- 允许修改或调查的范围、禁止范围与所需权限；
- 可实际执行的验证方式、停止条件和希望返回的内容。

只读取本次需要的 `.agent-fabric/roles/*.md`。可以用 `.agent-fabric/contracts/` 帮助表达任务，但以语义完整为准，不套固定模板。

完成条件：每个准备委派的任务都有明确结果、单一所有权、边界和可检查的完成标准；仍会改变方案的歧义已经解决或交回用户。

## 2. 选择 Role 与协作者

读取 `.agent-fabric/local/resolution.json`，按任务需要选择已由用户确认的 Role、协作者、模型和调用方式。

- 小任务可以由当前 Agent 直接完成，不为使用多 Agent 强行拆分。
- 只有所有权不重叠且互不依赖的任务才并行；共享文件或前后依赖任务保持串行。
- 配置缺失、过期或不可用时，转入 [`configure-collaborators.md`](configure-collaborators.md)，不静默改用其他协作者、模型、provider、调用方式或权限。
- Reviewer 只有在 Agent、模型和上下文都与执行者独立时才算独立审查；否则明确称为“自审”。

完成条件：每个委派都解析到当前可用的协作者，没有所有权冲突；任何不可用路由及其影响都已向用户说明。

## 3. 发出完整委派

使用当前环境实际提供的原生委派、CLI、浏览器或连接器直接协作。每份委派至少让协作者理解：

- 目标和必要背景；
- 自己拥有的文件或职责，以及需要保留的其他改动；
- 接口、约束、权限和停止条件；
- 验证方式与希望返回的证据。

协作者不是独自在项目中工作。要求它保留用户和其他协作者的改动，在既定方向内判断实现细节；遇到范围冲突、关键歧义或验证失败时报告，而不是自行重定产品方向。

完成条件：协作者无需猜测隐藏背景即可执行，并且实际调用的身份、模型、方式和权限与用户确认的配置一致。

## 4. 把返回结果视为声明

`orchestrator` 必须理解自由格式结果，并用当前项目的真实证据复核：

1. 查看实际文件、改动或来源，而不只阅读协作者摘要。
2. 确认变化都在约定范围内，并保留了其他人的工作。
3. 在可行时亲自重跑关键验证；否则说明无法重跑的原因。
4. 将证据与目标、接口、约束和完成标准逐项对照。

结果有误时，优先把精确修正交回原协作者。若由 `orchestrator` 接管或更换协作者，明确说明原因和责任变化；不以静默补丁或 silent fallback 掩盖失败。任何修正都会使此前针对旧结果的审查失效，必须重新复核。

完成条件：每项被采用的结论或改动都有主 Agent 检查过的证据；修正后的完整结果已经重新验证。

## 5. 留存与交付

外部结果默认是 `ephemeral`：

- 未采用且无需排错：丢弃。
- 被采用为重要结论、实现依据或验证证据，或用户要求保存：整理后写入 `.agent-fabric/records/<task-id>/`。
- 失败或需要排错：只把必要材料写入默认不进 Git 的 `.agent-fabric/local/traces/<run-id>/`。

记录保留理解结果所需的最少内容。完整对话、凭据或敏感原文只有在确有必要且用户确认后才保存；远端服务自己的留存要与项目记录分开说明。

最终由 `orchestrator` 告诉用户：完成了什么、采用了哪些协作者结果、实际验证了什么、保存了什么，以及还剩哪些限制或决定。

完成条件：最终交付由实际证据支持；留存位置与采用状态一致；未采用内容和敏感内容没有被默认持久化。
